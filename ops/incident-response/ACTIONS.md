# Trusted incident workflow — #228

Implementation is default-disabled and has no configured model, spending authority, credentials or live acceptance evidence. The MVP runtime path is automatic: triage, one fixer execution, fresh review, candidate PR checks, squash merge, development verification and recovery, then exact production promotion and recovery. A later human approval option is outside this MVP. Initial setup and resource activation remain separately reviewed.

## Credential boundaries

The receiver's dispatch App and the publisher App are separate identities. The publisher App needs Contents write, Pull requests write, Issues write and **Administration read** on this repository only. Administration write is rejected. The read permission is an explicit one-time App/installation setup amendment; this implementation does not change an App or installation.

Trusted preflight, publisher and merge jobs independently mint an owner-only, repository-selected token containing Administration read only. It can inspect exact repository identity and classic `main` protection. A successful repository identity read plus the verified mint response establishes read capability before a protection 404 is accepted as absence. Missing capability, hidden repository 404, permission failure, unknown response or existing classic protection denies admission; existing classic policy needs reviewed migration into the canonical rulesets. The full active/inherited ruleset inventory is checked before admission and again before publication/merge. Unsupported policy, bypass actors or any human/CodeOwner/last-push approval requirement denies; required frontend/backend checks, strict matching main, squash, thread resolution, deletion and force-push protections remain.

Publication and merge tokens omit Administration read. Their deterministic brokers permit only incident branch/PR creation or the exact candidate's squash merge. The production promoter receives only `GITHUB_TOKEN`, with Actions write for its fixed workflow dispatch operation. GitHub scopes are repository-wide capabilities: code and machine protections enforce the exact operation; scopes do not restrict dispatch to a single workflow or make PR write incapable of merging.

The model jobs receive no App key, publisher/protection token, Grafana token, AWS credentials or write-capable GitHub token. `OPENAI_API_KEY` is exposed only to a trusted setup process, which passes it to a job-local gateway through stdin. The pinned Action receives a random local bearer. A distinct, non-sudo UID runs the pinned CLI. Runner-owned sticky `CODEX_HOME` permits CLI operational files while protecting runner-owned configuration and its parent directory; a real distinct-UID test verifies those boundaries.

## Required setup

Keep `PAWLOCAL_ONCALL_ENABLED` unset/false until setup and development acceptance are reviewed. Configure the protected on-call Environments, exact dispatch bot actor, App identities/private key, distinct read-only Grafana Stack service-account token and public bindings. The Stack token is not a Cloud Access Policy ingestion token or provisioning administrator. Free-tier Viewer access may be stack-wide; trusted code enforces environment/release payload scope. Production telemetry access requires the explicit protected read approval, rechecked in follow-up phases. No model receives that token.

Every runtime target (`development`, `production`, their matching `-plan`/`-apply`, and both `oncall-` Environments) must allow only main and have no runtime reviewer/wait/custom approval gate. Setup, IAM bootstrap and destroy protections remain separate. This code verifies settings, never edits them or uses a bypass actor. Missing configuration denies before model admission.

Readiness requires `PawLocal change authorization` pinned to the configured publisher App ID (never any source or the generic GitHub Actions issuer), alongside real CI. A separately implemented authorizer must validate immutable incident lineage or an owner-approved ordinary PR, and gate all shared production/infrastructure entrypoints before credentials. Its proposed publisher App commit-statuses-write permission and status-only token phase are not implemented by this PR; the current mint safelist deliberately remains unchanged. Moving approved production monitoring/read/release setup before a development-origin full-loop demonstration is a proposed sequencing amendment, pending the owner's decision. This code does not amend that acceptance criterion, activate production access or silently substitute a reduced demonstration.

Set `PAWLOCAL_ONCALL_MODEL_PROFILE` only after owner selection, current pricing/entitlement review and quota approval. No model name, rate or spend amount is defaulted. The complete JSON schema is `quota.Profile`; it requires model/effort/Standard tier, conservative integer rates in microdollars per million tokens, monthly run and spending ceilings, per-request and cumulative two-role token/request envelopes, approval reference, current approved UTC month, official rate provenance and bounded expiry. It also requires the bounded machine release duration, recovery duration and actual per-environment rule UIDs. Fixture values in tests are not live approval.

Globally serialized admission claims the incident generation and reserves both roles' complete worst-case envelope in the protected fixed issue ledger before any model execution. Failed, cancelled or uncertain attempts remain charged; there is no automatic refund, retry or second attempt. The gateway counts the complete explicit request, enforces token/request limits before forwarding, fixes Standard tier/output caps, rejects remote tools/stored state/files/images, and charges allocations before forwarding. Logged allocations are conservative reservations, not a claim of provider-billed usage. Interactive subscriptions do not fund unattended API calls.

## Deadlines and recovery

The controller always supplies `expected_workflow_sha` equal to its reviewed
release commit when dispatching the fixed production workflow on main. A
credential-free entry job rejects a malformed assertion or changed workflow SHA
before calling Terraform or any publisher job. The controller also validates
the fetched production run's exact head SHA. An ordinary manual promotion can
leave this optional assertion blank to select an older verified release with
current trusted workflow code. The assertion only narrows execution: it never
authenticates incident authority or replaces the pending #245 gate.

The admission/model/check/review/PR phase has one absolute 20-minute budget, including subsequent job scheduling delays. The machine CI/development/production/recovery phase uses the explicit approved profile duration, at most 60 minutes, starting at publication. The latter never extends model work. Kernel alarms and bounded subprocess/HTTP operations enforce work deadlines; GitHub queue/cancellation latency can delay the workflow's terminal UI status beyond them.

Public recovery URLs reuse the existing source keys: `config/frontend/base-url` and `config/api/base-url`, copied into matching on-call Environments as `PAWLOCAL_PUBLIC_BASE_URL` and `VITE_API_BASE_URL`. They are checked against reviewed Grafana bindings; no alert or model supplies a URL. Recovery must observe the approved stable window, public journey and fresh scoped signal/rule health. An absent alert alone is insufficient.

Development recovery finishes before production dispatch. Each environment may settle under the same machine deadline, then must remain healthy continuously for its approved window (at least 600 seconds). A regression after that window starts escalates; it never silently resets the window or extends the deadline. Bound receipts record the actual release, deployment run, profile and observation times. The finalizer closes the incident only after verifying both receipts and current production identity. Missing evidence leaves an escalated or uncertain incident.

Closing the protected owner-marked quota ledger is the live global stop; closing the claimed incident stops that generation. Trusted code rereads both before model requests, observations and mutations. Protected Environment variable changes apply at job boundaries, so do not treat them as instantaneous revocation inside an already running job. Use workflow cancellation for running model work, and reconcile any already accepted release operation. After a stop or deadline the finalizer records uncertainty locally without new GitHub writes; it retains the consumed claim and reservation.

Offline Linux checks ran the pinned CLI as a distinct unprivileged UID against a local dummy endpoint, and ran the actual backend place tests, frontend Vitest tests and Vite build against immutable dependencies with only the tool-cache directories writable. A credential-free CI test creates a venv from the actual setup-python interpreter, proves distinct-UID execution, and rejects a private ancestor before restoring access. The local Linux fixture passes; hosted CI evidence must be recorded separately. Runtime preparation also executes exact trusted `pytest --version` as the model UID before starting the gateway, so interpreter/dependency traversal failure cannot consume model usage. Actual hosted Action execution and complete live release/recovery remain acceptance checks.

On uncertainty, cease new release mutations. Never blindly interrupt an in-flight Terraform apply, redispatch an uncertain request, extend a model budget, perform arbitrary infrastructure rollback or claim recovery from missing data. Keep the incident generation/reservation consumed and reconcile the actual release through the linked run/deployment evidence. Live App scopes, exact hosted API response formats, decrypted secret lifecycle and end-to-end Grafana/release recovery remain acceptance gates until demonstrated.

## Token usage summaries

Every responder run appends an admission preview and an overall Actions job summary in **Record incident outcome**, including when preflight does not claim an incident and subsequent jobs skip. Fixer and fresh review also append summaries with `always()`. The existing incident finalization mutation still requires a claimed issue. No inference, release, quota, or approval behavior is changed by reporting.

The trusted runner gateway writes mode-0600 atomic numeric snapshots to `oncall-trusted/gateway-usage.json` before forwarding a charged inference request and after reading usage. A bounded Responses JSON response or terminal SSE event supplies provider input/output counts, cached input and reasoning output. The parser tolerates network chunk boundaries and never persists response text, prompts, tool content or credentials. Cached input and reasoning output are subsets of input and output, respectively, and must not be added again. See the official [token counting guidance](https://developers.openai.com/api/docs/guides/token-counting).

Use the overall view to compare provider tokens with the full configured **two-execution** ceiling, including skipped executions. Per-execution and per-request rows show counted input, full output allowance charged, observed actual usage and headroom against each independent limit. The effective output allowance may be smaller than the configured per-request limit because `output_per_role // requests_per_role` must leave room for every turn. Model, reasoning effort and service tier explain the profile used. Gateway failure/quota-denial counts and responses ending at `max_output_tokens` identify limits worth investigating alongside the existing raw diagnostics.

Missing, malformed or interrupted usage remains **unknown**, never inferred as zero. A failed job may retain usable observations; skipped jobs retain their workflow result and missing-report label. If GitHub cannot deliver a job output, or a runner is lost before its reporting step, aggregate totals and charged allocations are explicitly partial. Preflight is a limits preview, not a usage measurement. Costs use approved worst-case input/output rates without cached discounts and are estimates, not bills. The upfront monthly reservation remains the full fixer plus reviewer envelope, even when actual usage is lower or work skips/fails; reports never settle/refund the ledger or change limits. Remaining monthly balance requires the protected ledger, not these usage observations.
