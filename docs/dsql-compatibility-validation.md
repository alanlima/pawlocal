# Aurora DSQL compatibility review

**Review date:** 2026-10-18
**Status:** Static review of the current PawLocal repository and AWS documentation. No DSQL cluster was provisioned or queried. A live compatibility test is still required before selecting DSQL. The owner has approved MVP budget; backup, HA, recovery, and telemetry are outside the MVP scope.

The approved Issue #53 prototype is now recorded in [the prototype note](dsql-facilities-prototype.md), with its generated [schema](generated/dsql-facilities-schema.sql) and [query](generated/dsql-facilities-prototype.sql). None of this validates DSQL execution, live index completion, production migration/backfill, IAM/OCC behavior, DPU usage, or cost. Backup, HA, recovery, and restore are no longer MVP compatibility gates; they are deferred to [Issue #44](https://github.com/alanlima/pawlocal/issues/44).

## Local and cloud database configuration boundary

Docker Compose keeps its PostgreSQL container as the default database for local development and tests. The cloud deployment target is Aurora DSQL only after this document's compatibility and approval gates pass. Do not make a change to the local Compose database URL as part of selecting a cloud database. A cloud development deployment may use Aurora DSQL only when its environment-specific configuration explicitly selects the DSQL adapter/credentials; the current generic `PAWLOCAL_DATABASE_URL` alone does not configure the AWS dialect or IAM token lifecycle. Production and development cloud endpoints and credentials remain isolated.

| --- | --- | --- | --- |
| Driver and SQLAlchemy | SQLAlchemy 2 with `postgresql+psycopg`; normal `create_engine` initialization | PostgreSQL wire protocol and psycopg are supported, but AWS provides a separate SQLAlchemy dialect that handles IAM tokens, TLS defaults, and DSQL initialization differences. | **Blocker.** Add/configure the AWS DSQL dialect and its credential chain. The existing generic engine is not validated; default psycopg dialect initialization may attempt unsupported savepoint behavior. |
| IAM from Lightsail | `database_url`/host settings accept database credentials; no AWS identity provider is configured | DSQL requires IAM-generated short-lived DB authentication tokens. Lightsail IAM docs describe instance profiles for EC2 applications and do not establish an equivalent role attachment for Lightsail instances. | **Blocker.** Specify and prove a secure, short-lived runtime credential source/role assumption from Lightsail. Never add static AWS keys to the image or environment. |
| UUID, text, varchar, boolean, timestamps, numeric/float | UUID primary keys; bounded strings, text, booleans, timezone timestamps, and float ratings | These types are in DSQL's supported type families. | Likely compatible at type level; still validate generated DDL, defaults, and round trips through the AWS dialect. |
| Facilities persistence | The ORM declares `JSON` with a PostgreSQL `ARRAY(varchar(80))` variant; the production PostgreSQL migration 0001 creates the native array column and 0004 adds an array-containment check. JSON/JSONB is supported. The non-PostgreSQL `json_each` branch is not evidence of DSQL JSON query compatibility. | **Blocker.** Replace the stored representation (candidate: JSONB or a normalized relation) and adapt serialization, validation, filters and migrations; verify existing `ANY(array)` behavior is not carried over unchanged. Issue #53's isolated normalized-relation prototype is only a candidate for further live validation. |
| Place search / filters / order / count / pagination | `ILIKE` over name/area/category, exact area/category predicates, per-facility `ANY(array)`, count subquery, name/UUID ordering, offset/limit | PostgreSQL-like SQL is only supported as documented; array-column predicate is incompatible with the current schema. DSQL is not full PostgreSQL. | **Blocker for current query.** Rework facility containment for the selected persisted type; verify escaped `ILIKE`, combined filters, deterministic ordering, exact count, and pagination against DSQL. Capture `EXPLAIN ANALYZE` and CloudWatch DPU metrics for representative seeded data. |
| Favourites idempotency | Composite primary key `(user_subject, place_id)`; duplicate insert is caught as `IntegrityError` and treated as already present | Primary/unique constraints are supported; DSQL can return serialization/conflict errors for concurrent work. | Validate duplicate and concurrent insert semantics; avoid suppressing unrelated integrity failures if adapting error handling. |
| One review per author/place | Partial unique index on contributor/place where `kind='review'`; repository translates `IntegrityError` to `DuplicateReviewError` | DSQL supports partial unique indexes, but index creation is asynchronous and DSQL failures may use serialization errors as well as uniqueness errors. | Validate dialect emission, async index job completion, duplicate response mapping, and concurrent duplicate submissions. |
| Contributions, reports, ratings, transactions | Review writes use `SELECT ... FOR UPDATE`, insert, average aggregation/update, then commit; reports/favourites use foreign keys | DSQL supports foreign keys, checks, and `ON DELETE CASCADE`. `FOR UPDATE` uses optimistic conflict detection at commit; it is not a row lock. Conflicts return SQLSTATE `40001` / OCC codes and applications should retry idempotently. | **Blocker.** Add bounded, idempotent retry around the complete transaction and test review uniqueness/rating projection under concurrent writes. Decide if CASCADE cardinality respects DSQL transaction limits. Validate AVG, joins, checks, FK semantics and report targets. |
| Alembic clean install and later upgrade | Migrations 0001-0006 use synchronous `CREATE INDEX` / `op.create_index`, PostgreSQL ARRAY DDL, regex checks, CTAS/casts, constraint add/drop, and data-moving operations. Revision 0005 combines column DDL, backfill DML, added foreign keys, and further DDL; revision 0006 creates quarantine tables, copies/deletes rows, recomputes ratings, and adds constraints in one migration. | DSQL requires DDL and DML in separate transactions, permits only one DDL statement per transaction, and limits a transaction to 3,000 modified rows. Index creation uses `CREATE INDEX ASYNC` and returns a job that must complete before dependent work. Adding foreign keys to existing tables requires a DSQL-specific `NOT VALID`/asynchronous validation path. | **Blocker.** Introduce explicit DSQL engine/credential configuration for both the application and Alembic, then design a DSQL-specific migration sequence that separates DDL/DML, chunks data work within transaction limits, adds/validates existing-table constraints as DSQL requires, and waits for async indexes. | Backup, recovery, persistence boundary | Local Compose stores PostgreSQL in a named volume; deployment is not implemented | DSQL stores data outside replaceable app VMs and supports AWS Backup. | Search/geospatial future | Current MVP uses text substring search and curated exact area labels; no PostGIS/geospatial query in this reviewed code | DSQL supports a subset of PostgreSQL features and types; this review does not establish PostGIS or future geographic/text-search parity. | Keep geographic and advanced-search capabilities out of the DSQL compatibility claim. Revisit before adding those features. |

## Current conclusion

Aurora DSQL is available in Sydney and has an AWS-supported SQLAlchemy adapter, IAM token generation, TLS support, and regional multi-AZ behavior. However, the current PawLocal implementation cannot be called compatible: the persisted native array, default connection setup, migration/index path, and retry/credential design need work. These are material blockers. Keep DSQL as the human's preferred candidate pending validation, and compare RDS for PostgreSQL or encrypted Lightsail managed PostgreSQL if they cannot be resolved.

## Reproducible compatibility validation gate

The owner has approved the MVP budget. Use disposable, isolated Sydney test resources within that approved MVP scope, a short-lived IAM credential chain, and synthetic data only; never point this procedure at production. No test cluster has been created yet.

1. Introduce an explicit engine and credential configuration seam: the application currently creates a module-global psycopg engine directly, and Alembic creates a separate engine. Then add/configure the AWS DSQL dialect and short-lived credential chain for both paths, with TLS verification. Do not put an auth token in a committed URL.
2. Convert the facilities storage and query strategy, then generate migrations using the AWS DSQL dialect. Inspect all SQL emitted by the migration tool and lint generated SQL with [AWS `dsql-lint`](https://github.com/awslabs/aurora-dsql-tools/tree/main/dsql-lint).
3. On the disposable cluster, run (a) Alembic upgrade from empty, (b) upgrade from the previous migration revision with representative legacy rows, then (c) the `test_postgres_repositories_constraints_and_records_survive_new_sessions` journey from `backend/tests/test_postgres_integration.py`, adapted to the DSQL engine/credentials. Confirm fixtures clean up after themselves.
4. Extend that journey with concurrent duplicate review submissions, concurrent rating writes, retry exhaustion, a cold/new connection after token refresh, and a replaceable-VM reconnect. Record errors/SQLSTATEs without logging SQL bind values, tokens, user subjects, or contribution bodies.
5. Seed representative place and contribution volumes. Exercise combined text/area/category/facility filters, ordering, exact counts and page boundaries. Capture elapsed time, query plans and the directional statement estimate from `EXPLAIN ANALYZE VERBOSE`, plus CloudWatch `ComputeDPU`, `ReadDPU`, and `WriteDPU` and transaction totals. AWS's statement estimate is not billing-grade; reconcile measured workload totals with CloudWatch and billing before extrapolating a monthly price. Do not multiply API request count by a guessed DPU factor.
6. Record the measured DPU usage and the Sydney rate-card version. Backup retention, restore drills, and achieved RPO/RTO are deferred to Issue #44.

**Evidence still required:** an actual clean migration, upgrade migration, repository journey, conflict/retry result, token refresh/new connection, and query DPU sample. None is claimed complete in this static review. Keep DSQL provisional until compatibility and credentials are validated; the owner-approved MVP budget does not approve deferred backup/HA/recovery work.
