# Aurora DSQL compatibility review

**Review date:** 2026-10-18  
**Status:** Static review of the current PawLocal repository and AWS documentation. No DSQL cluster was provisioned or queried. A live compatibility and cost test is still required before selecting DSQL.

## Scope inspected

Reviewed `backend/pawlocal/infrastructure/models.py`, `places.py`, `community.py`, `contributions.py`, `database.py`, `backend/migrations/versions/0001` through `0006`, `backend/tests/test_postgres_integration.py`, `backend/pyproject.toml`, and `backend/alembic.ini`. The local PostgreSQL integration test is a useful starting journey, but has not been run against DSQL and cannot establish DSQL support.

## Compatibility matrix

| Requirement | Current PawLocal implementation | DSQL support/evidence | Finding / work before a live test |
| --- | --- | --- | --- |
| Driver and SQLAlchemy | SQLAlchemy 2 with `postgresql+psycopg`; normal `create_engine` initialization | PostgreSQL wire protocol and psycopg are supported, but AWS provides a separate SQLAlchemy dialect that handles IAM tokens, TLS defaults, and DSQL initialization differences. | **Blocker.** Add/configure the AWS DSQL dialect and its credential chain. The existing generic engine is not validated; default psycopg dialect initialization may attempt unsupported savepoint behavior. |
| IAM from Lightsail | `database_url`/host settings accept database credentials; no AWS identity provider is configured | DSQL requires IAM-generated short-lived DB authentication tokens. Lightsail IAM docs describe instance profiles for EC2 applications and do not establish an equivalent role attachment for Lightsail instances. | **Blocker.** Specify and prove a secure, short-lived runtime credential source/role assumption from Lightsail. Never add static AWS keys to the image or environment. |
| UUID, text, varchar, boolean, timestamps, numeric/float | UUID primary keys; bounded strings, text, booleans, timezone timestamps, and float ratings | These types are in DSQL's supported type families. | Likely compatible at type level; still validate generated DDL, defaults, and round trips through the AWS dialect. |
| Facilities persistence | `places.facilities` is PostgreSQL `ARRAY(varchar(80))`; migration 0001 creates that native array column. | DSQL's supported array documentation describes arrays as query-runtime values, not a supported persisted table column type. JSON/JSONB is supported. | **Blocker.** Replace the stored representation (candidate: JSONB) and adapt serialization, validation, filters and migrations; verify existing `ANY(array)` behavior is not carried over unchanged. |
| Place search / filters / order / count / pagination | `ILIKE` over name/area/category, exact area/category predicates, per-facility `ANY(array)`, count subquery, name/UUID ordering, offset/limit | PostgreSQL-like SQL is only supported as documented; array-column predicate is incompatible with the current schema. DSQL is not full PostgreSQL. | **Blocker for current query.** Rework facility containment for the selected persisted type; verify escaped `ILIKE`, combined filters, deterministic ordering, exact count, and pagination against DSQL. Capture `EXPLAIN ANALYZE` and CloudWatch DPU metrics for representative seeded data. |
| Favourites idempotency | Composite primary key `(user_subject, place_id)`; duplicate insert is caught as `IntegrityError` and treated as already present | Primary/unique constraints are supported; DSQL can return serialization/conflict errors for concurrent work. | Validate duplicate and concurrent insert semantics; avoid suppressing unrelated integrity failures if adapting error handling. |
| One review per author/place | Partial unique index on contributor/place where `kind='review'`; repository translates `IntegrityError` to `DuplicateReviewError` | DSQL supports partial unique indexes, but index creation is asynchronous and DSQL failures may use serialization errors as well as uniqueness errors. | Validate dialect emission, async index job completion, duplicate response mapping, and concurrent duplicate submissions. |
| Contributions, reports, ratings, transactions | Review writes use `SELECT ... FOR UPDATE`, insert, average aggregation/update, then commit; reports/favourites use foreign keys | DSQL supports foreign keys, checks, and `ON DELETE CASCADE`. `FOR UPDATE` uses optimistic conflict detection at commit; it is not a row lock. Conflicts return SQLSTATE `40001` / OCC codes and applications should retry idempotently. | **Blocker.** Add bounded, idempotent retry around the complete transaction and test review uniqueness/rating projection under concurrent writes. Decide if CASCADE cardinality respects DSQL transaction limits. Validate AVG, joins, checks, FK semantics and report targets. |
| Alembic clean install and later upgrade | Migrations 0001-0006 use synchronous `CREATE INDEX` / `op.create_index`, PostgreSQL ARRAY DDL, regex checks, CTAS/casts, constraint add/drop, and data-moving operations. | DSQL index creation uses `CREATE INDEX ASYNC`; its SQLAlchemy dialect emits async index syntax. DDL is distributed and can cause retryable catalog-version conflicts. Feature support varies from PostgreSQL. | **Blocker.** Run the real Alembic chain using the DSQL dialect on a clean test cluster, then run an upgrade from a fixture at the preceding revision. Validate backfills/quarantine/constraints and wait for async index jobs. Do not treat offline SQL or local PostgreSQL as this proof. |
| Backup, recovery, persistence boundary | Local Compose stores PostgreSQL in a named volume; deployment is not implemented | DSQL stores data outside replaceable app VMs and supports AWS Backup. A Lightsail VM remains a single-app-host failure domain. | Configure and price backup retention, perform restore drill, record RPO/RTO, and verify app recovery after VM replacement before production. |
| Search/geospatial future | Current MVP uses text substring search and curated exact area labels; no PostGIS/geospatial query in this reviewed code | DSQL supports a subset of PostgreSQL features and types; this review does not establish PostGIS or future geographic/text-search parity. | Keep geographic and advanced-search capabilities out of the DSQL compatibility claim. Revisit before adding those features. |

## Current conclusion

Aurora DSQL is available in Sydney and has an AWS-supported SQLAlchemy adapter, IAM token generation, TLS support, and regional multi-AZ behavior. However, the current PawLocal implementation cannot be called compatible: the persisted native array, default connection setup, migration/index path, and retry/credential design need work. These are material blockers. Keep DSQL as the human's preferred candidate pending validation, and compare RDS for PostgreSQL or encrypted Lightsail managed PostgreSQL if they cannot be resolved.

## Reproducible validation gate (requires separately approved test resources)

No command below creates a cluster. First get an explicit, separate approval for any DSQL test cluster and its spend estimate. Use a disposable, isolated Sydney test cluster/account, a short-lived IAM credential chain, and synthetic data only; never point this procedure at production.

1. Add the AWS-maintained [`aurora-dsql-sqlalchemy`](https://github.com/awslabs/aurora-dsql-orms/tree/main/python/sqlalchemy) adapter behind the existing database-engine seam; configure TLS verification and a short-lived credential provider. Do not put an auth token in a committed URL.
2. Convert the facilities storage and query strategy, then generate migrations using the AWS DSQL dialect. Inspect all SQL emitted by the migration tool and lint generated SQL with [AWS `dsql-lint`](https://github.com/awslabs/aurora-dsql-tools/tree/main/dsql-lint).
3. On the disposable cluster, run (a) Alembic upgrade from empty, (b) upgrade from the previous migration revision with representative legacy rows, then (c) the `test_postgres_repositories_constraints_and_records_survive_new_sessions` journey from `backend/tests/test_postgres_integration.py`, adapted to the DSQL engine/credentials. Confirm fixtures clean up after themselves.
4. Extend that journey with concurrent duplicate review submissions, concurrent rating writes, retry exhaustion, a cold/new connection after token refresh, and a replaceable-VM reconnect. Record errors/SQLSTATEs without logging SQL bind values, tokens, user subjects, or contribution bodies.
5. Seed representative place and contribution volumes. Exercise combined text/area/category/facility filters, ordering, exact counts and page boundaries. Capture elapsed time, query plans/`EXPLAIN ANALYZE` DPU estimate and CloudWatch `ComputeDPU`, `ReadDPU`, and `WriteDPU`. Extrapolate from measured query mix and measured storage to monthly price; do not multiply API request count by a guessed DPU factor.
6. Test AWS Backup retention and a restore drill, then record the achieved RPO/RTO. Record the exact account free-tier interpretation and Sydney rate-card version.

**Evidence still required:** an actual clean migration, upgrade migration, repository journey, conflict/retry result, token refresh/new connection, query DPU sample, and backup restore. None is claimed complete in this static review. Until the test is separately authorized and run, keep DSQL provisional and keep provisioning/cost approval open.
