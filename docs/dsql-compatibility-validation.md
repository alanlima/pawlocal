# Aurora DSQL compatibility review

**Review date:** 2026-10-19

**Status:** The owner confirmed Lightsail + Aurora DSQL with an access-key runtime and authorized one-off CLI key creation after Terraform creates the app IAM users. Credential values must remain in local or GitHub Actions environment variables/secrets and must not enter Terraform inputs, outputs, state, plans, or logs. Terraform now includes an idempotent DSQL custom-role/IAM mapping bootstrap invoked during apply, and the Lightsail adapter is being updated to deliver environment-scoped credentials over SSH stdin. Neither path has been live validated. See [Issue #43](https://github.com/alanlima/pawlocal/issues/43). Review the implementation at commit `00ee8f0708320a6d634da39d412c5997fa811212` on PR #61. Its earlier Backend CI, full-stack backend/frontend checks, standalone frontend checks, workflow validation, and GitGuardian passed; those checks do not establish live DSQL behavior. The DSQL SQLAlchemy engine path, clean-install baseline/runner, normalized facility schema and compatible queries, bounded pre-commit OCC retries, and reserved-role rejection are implemented. Live migration, connection/token refresh, access-key use, and OCC behavior remain unverified.

## Scope and release boundaries

This review covers DSQL schema/query compatibility and migration preparation for the MVP. Local Docker Compose continues to use PostgreSQL. No provider switch, cloud resource creation, deployment, or DSQL connection was performed. The initial cloud release keeps telemetry disabled; telemetry enablement remains tracked by [Issue #59](https://github.com/alanlima/pawlocal/issues/59).

Backup, HA, restore, RPO/RTO, and recovery are excluded from this release and deferred to [Issue #44](https://github.com/alanlima/pawlocal/issues/44), to be reviewed after the MVP is deployed to cloud. They are not gates for this DSQL compatibility work.

## Current implementation and compatibility matrix

| Area                         | Current implementation                                                                                                                                                                                                                                                                                                                                   | Evidence and limitation                                                                                                                                                                      |
| ---------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Facilities schema            | `PlaceRecord` maps facilities through normalized `place_facilities` rows. PostgreSQL migration `0007` converts legacy arrays while preserving ordinal order. Discovery and favourite reads eager-load facility rows in one batched `selectinload` query instead of one query per returned place.             | Local backend tests include repository query-count assertions for both discovery and favourites. PostgreSQL offline Alembic SQL generation only; no live PostgreSQL migration was run for this worktree. |
| Place search                 | The application uses a correlated `EXISTS` predicate per distinct selected facility. The query no longer uses PostgreSQL `ANY(array)` or a JSON-specific branch.                                                                                                                                                                                         | The production query compiles with the AWS SQLAlchemy DSQL dialect and the generated search/count SQL passes `dsql-lint`. This is offline SQL evidence, not execution or a query-plan check. |
| DSQL clean install           | A separate static SQL baseline at `backend/migrations/dsql/0001_initial/` creates the normalized final schema directly. `pawlocal.dsql_migrations.apply_dsql_baseline(engine)` runs one DDL statement per transaction, records a version only after the schema succeeds, and provides bounded row-by-row DML batches for future data changes.            | Fake-engine unit tests exercise transaction separation, ledger ordering, rerun behavior when DDL exists, and the DML batch cap. The baseline has not been applied to a DSQL cluster.         |
| Async indexes                | The runner waits for each returned index job. It then checks the DSQL catalog for a valid index and compares its table, uniqueness, method, ordered columns, and predicate to the requested definition. If `IF NOT EXISTS` returns no job ID, the runner performs the same verification and fails closed if the index is missing, invalid, or different. | Unit/fake-catalog tests plus AWS dialect/linter checks only. Index completion and catalog-query behavior remain unverified against a live cluster.                                           |
| PostgreSQL migration history | Alembic revisions `0001`-`0008` remain the local/PostgreSQL path. The generic Alembic environment rejects DSQL URLs before importing application models or rendering offline SQL, and checks online connections before running revisions.                                                                                                                                     | PostgreSQL offline `alembic upgrade head --sql` succeeds through `0008`. A manual offline DSQL-URL invocation exits at the early guard before revision SQL. No live migration was run. |
| Legacy cloud data            | No PostgreSQL-to-DSQL import/backfill sequence is implemented.                                                                                                                                                                                                                                                                                           | The DSQL baseline is suitable only for an empty initial cloud database. Existing PostgreSQL data migration is still required if the deployment starts with non-empty legacy data.            |
| Runtime engine and IAM       | Application startup recognizes `auroradsql+psycopg` and uses AWS's `create_dsql_engine` helper, which delegates IAM token generation to the AWS DSQL connector and SDK default credential chain. The DSQL transaction hook sets `search_path` locally to the Terraform-bootstrapped `pawlocal` schema. The candidate Terraform bootstrap creates each custom role, IAM mapping, user schema, and `USAGE, CREATE` grants in separate transactions. Access keys remain outside Terraform state and plans; one-off CLI issuance is authorized after Terraform creates the IAM principals. | Offline tests build and inspect the engine and bootstrap transaction boundaries without connecting. No live DSQL connection, schema migration, token refresh, or least-privilege behavior is validated yet. |
| OCC behavior                 | Review retries are limited to recognized DSQL conflict errors before commit. Errors from the post-commit refresh are propagated and never replay the contribution; PostgreSQL remains single-attempt.                                                                                                                                                           | Unit tests cover bounded retries and a retryable refresh failure after a successful commit; no DSQL OCC response, concurrency, or retry-exhaustion scenario was observed live.                |
| CI checks                    | Backend CI installs the DSQL tools and lints the checked-in baseline plus generated application search/count SQL.                                                                                                                                                                                                                                      | On implementation commit `00ee8f0`, standalone Backend CI/frontend checks, full-stack backend/frontend checks, workflow validation, and GitGuardian passed. Image publication and development deployment were skipped because this was a PR. This does not validate DSQL runtime behavior. |

The current DSQL baseline deliberately does not replay PostgreSQL migrations `0001`-`0008`. Those revisions include a persisted PostgreSQL array, synchronous index creation, PostgreSQL-specific `unnest`/regex/CTAS operations, and multi-statement or mixed DDL/DML transformations. A separate baseline avoids applying those operations to DSQL, but it does not migrate existing records or provide forward DSQL upgrades beyond its initial revision.

- Generated application search/count SQL lint: passed.

On implementation commit `00ee8f0` in PR #61, the standalone Backend CI/frontend checks, full-stack backend/frontend checks, workflow validation, and GitGuardian passed; the immutable-image publication and development deployment jobs were skipped as expected for a PR. Passing CI, local tests, lint, compilation, offline migration generation, and fake-engine/catalog tests do not establish that DSQL accepts or executes the statements, that indexes become valid, or that queries have acceptable behavior or cost. No DSQL cluster or other DSQL resources were created or available for validation. No live DSQL compatibility claim is made.

## Remaining implementation and validation

The database provider and access-key runtime direction are selected. Terraform creates the DSQL clusters and IAM app users/policies, while the expressly authorized one-off CLI step creates access keys only after those users exist. Those key values must stay out of Terraform and be written only to the environment-scoped GitHub secrets and the requested Desktop TXT file; the approved deployment adapter transfers them to the corresponding Lightsail host through SSH stdin. Do not print or commit keys, or place generated DSQL tokens in application URLs. Live validation still requires the reviewed Terraform plan to be applied, followed by deployment and a successful migration. CloudTrail can store `DbConnect` audit events, but an alert destination has not been supplied.

After a DSQL test environment and its per-environment SDK credentials are configured, the remaining live DSQL validation is:

1. Apply the clean-install baseline to an empty test cluster and verify catalog objects, index validity, and schema constraints.
2. Exercise the repository/API journey, including place search, contributions, favourites, reports, duplicate review handling, rating updates, and bounded conflict retries.
3. Verify connection token refresh/reconnect and concurrent OCC behavior through the approved runtime identity path.
4. Capture representative query plans and DPU measurements before making performance or cost claims.
5. If cloud data already exists, design and test a separate PostgreSQL-to-DSQL import/backfill process with bounded DML; the current baseline does not provide it.

Telemetry remains disabled in the initial release; later enablement is tracked by [Issue #59](https://github.com/alanlima/pawlocal/issues/59). Backup, HA, restore, RPO/RTO, and recovery are excluded from this release and deferred to [Issue #44](https://github.com/alanlima/pawlocal/issues/44) for review after the MVP is deployed to cloud. They are not DSQL validation or deployment gates.
