# Stage 4 hosting and cost proposal

**Status:** Issue #75 accepts AWS Lightsail Container Services with Aurora DSQL. The prior Lightsail VM and long-lived DSQL-key runtime direction is superseded. Two unused CLI-created DSQL access keys were removed. Service-principal connectivity remains unverified against live DSQL. No AWS resources or deployments were changed by this implementation. Backup/HA/recovery remains deferred to [Issue #44](https://github.com/alanlima/pawlocal/issues/44); hosted telemetry remains deferred to [Issue #59](https://github.com/alanlima/pawlocal/issues/59).
**Pricing checked:** 2026-10-19 against current official AWS, Grafana, and GitHub pricing and documentation. Prices are USD before tax; Sydney/Australia region behavior is stated where it differs.

## Selected MVP direction

- **Application host:** Separate AWS Lightsail Container Services for development and production; keep Docker Compose for local development and the existing S3/CloudFront frontend.
- **Database:** Aurora DSQL in `ap-southeast-2` is selected by the owner. It is not a PostgreSQL drop-in for PawLocal; compatibility blockers and required validation are in [the DSQL compatibility note](dsql-compatibility-validation.md).
- **Database configuration boundary:** Local development and testing continue to use the PostgreSQL service in Docker Compose by default. Cloud deployments use the Aurora DSQL configuration after its compatibility and approval gates pass. Development may opt into Aurora DSQL only through an explicit development deployment/configuration change; do not switch local Compose to DSQL implicitly. Keep dev/prod data, credentials, configuration, deployment targets, and clusters separate, and promote the same tested application image from development to production.
- **Not selected:** DynamoDB and Lambda. Conventional PostgreSQL alternatives must be compared if DSQL's material compatibility issues cannot be resolved.
- Terraform provides each container service with an environment-scoped runtime principal and DSQL cluster policy/database-role mapping. No static access keys or SSH deployment are used. Live DSQL identity and connectivity validation remains required. GitHub deploy jobs use separate environment-scoped OIDC roles; Terraform's release role can create deployments only for its matching service.

Lightsail managed PostgreSQL automatically retains point-in-time recovery data for seven days; restoring creates a **new** database. ## DSQL compatibility and integration gate

The current backend branch contains a DSQL-specific SQLAlchemy engine path and clean-install baseline command using the AWS SDK credential chain. Neither the clean-install path nor runtime behavior has been exercised against a live DSQL cluster. See the matrix and gated runbook in [dsql-compatibility-validation.md](dsql-compatibility-validation.md).

Before confirming DSQL, inspect the actual schema, repositories and migrations; adapt where needed; then run a clean migration, an upgrade migration, and the existing repository integration journey against an isolated DSQL test cluster within the owner-approved MVP budget. The validation must cover search filters/count/pagination, favourites idempotency, duplicate review rejection, contribution/report persistence, referential integrity, rating aggregation, concurrent writes/conflict retries, connection refresh, and measured query DPUs to confirm the chosen design fits the approved budget. Local PostgreSQL passing is not evidence of DSQL compatibility. No DSQL cluster was created or queried for this proposal.

## Deployment, data and observability boundaries

- Treat Lightsail instances and containers as replaceable. Keep application state out of the VM filesystem; store uploads in external object storage if/when uploads exist. The current MVP has no uploaded media implementation.
- DSQL data is external to the VM. Separate the dev/prod database endpoints, users/roles and access policies. Backup retention, restore drills, RPO/RTO, HA, and recovery procedures are outside the MVP and deferred to Issue #44.
- Keep local Docker Compose wired to its PostgreSQL container by default. Select Aurora DSQL through deployment-specific cloud configuration only after the DSQL adapter, schema/migration path, authentication, and retry behavior pass. An Aurora-enabled cloud development environment must be an explicit opt-in in that environment's configuration; never make the local PostgreSQL setting silently resolve to Aurora. Recovery requirements are deferred to Issue #44.
- Lightsail's Terraform service principal supports service-side authorization, but available AWS documentation does not establish that a running container receives SDK credentials through it. The Terraform-managed DSQL policy/database role mapping replaces the old static access-key proposal; validate credential delivery, refresh, and database connectivity against a live environment before production promotion. The accepted design therefore remains implementation-ready but not live-compatible until this gate passes.
- CloudTrail DSQL `DbConnect` data-event capture is security audit logging, separate from application telemetry. The owner requires an alert on DSQL authentication events. Terraform currently defaults capture off; enabling it requires an owner-selected destination bucket, retention period, and alert destination because DSQL data events are billable and notifications need a target. These inputs remain a pre-apply blocker until selected. Keep application telemetry disabled for the initial release.
- Keep hosted telemetry disabled for the MVP. The Grafana Cloud/collector and browser-relay design belongs to Issue #59 and must not be enabled by the Issue #43 deployment workflows.
- Hosted alert delivery must reach an authenticated receiver that persists and deduplicates incidents before queueing any agent work. A webhook by itself does not launch an agent. Agent hosting and model usage are separate, unpriced follow-up work.
- Build and deploy the same immutable image from dev to prod. Confirm the repository remains public and uses standard GitHub-hosted runners, check artifact/cache usage against account quotas, and recheck current GHCR pricing policy. Dev rollback replays a release artifact from a previously verified successful deployment; production rollback selects a previous development-verified commit through the protected manual promotion workflow. Database recovery and data rollback remain deferred to Issue #44.
