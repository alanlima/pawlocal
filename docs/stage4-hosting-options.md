# Stage 4 hosting and cost proposal

**Status:** Human direction recorded 2026-10-18; technical validation and cost approval remain open. No resources are provisioned or approved for spending.
**Pricing checked:** 2026-10-19 against current official AWS, Grafana, and GitHub pricing and documentation. Prices are USD before tax; Sydney/Australia region behavior is stated where it differs.

## Direction under review

- **Application host:** AWS Lightsail. Run FastAPI as a Docker container on a Linux instance, keep Docker Compose for local development, and keep the existing S3/CloudFront frontend.
- **Database candidate:** Aurora DSQL in `ap-southeast-2` is preferred for investigation only. It is not yet a PostgreSQL drop-in for PawLocal; compatibility blockers and the required validation are in [the DSQL compatibility note](dsql-compatibility-validation.md).
- **Database configuration boundary:** Local development and testing continue to use the PostgreSQL service in Docker Compose by default. Cloud deployments use the Aurora DSQL configuration after its compatibility and approval gates pass. Development may opt into Aurora DSQL only through an explicit development deployment/configuration change; do not switch local Compose to DSQL implicitly. Keep dev/prod data, credentials, configuration, deployment targets, and clusters separate, and promote the same tested application image from development to production.
- **Not selected:** DynamoDB and Lambda. Conventional PostgreSQL alternatives must be compared if DSQL's material compatibility issues cannot be resolved.
- This direction authorizes documentation and investigation only. It does not approve a spend envelope, provisioning, `terraform apply`, or production migration. DRAFT-002 remains open.

## Issue #43 release policy (design only)

The requested full-stack CI/CD design is: run relevant tests/checks on pull requests; after merge to `main` and successful CI, publish a release and automatically deploy it to development; require a separate `workflow_dispatch` action to promote a release commit already verified in development to production. A merge to `main` must not automatically deploy the full-stack production release. The production workflow must validate main-branch ancestry, required CI, and successful development verification; promote the same backend image by immutable digest; serialize production deployment without canceling an active rollout; and retain deployment evidence and a documented manual rollback path.

Use separate GitHub `development` and `production` environments, frontend/API/database targets, data, secrets, and least-privilege deployment identities; use short-lived OIDC credentials where supported. Development hostname convention: `pawlocal-dev.<domain>`. Production: `pawlocal.<domain>`. Vite currently bakes configuration into the frontend build, so select public runtime configuration or a controlled environment-specific build from the same tested commit. Never include secrets in browser assets.

This is a documented target state, not an implemented workflow or an approved architecture/spend decision. The existing mock-backed static frontend remains on its current production workflow. Issue #43 acceptance must not be reported complete until the hosting/compatibility/recovery/cost decisions are approved, targets and credentials are configured, and CI/dev/prod and rollback evidence exists. The convention does not authorize DNS, certificates, new resources, deployment, or spending.

Each 2 GB database plan includes 80 GB SSD storage; this is substantially more provisioned storage than the 1 GB logical data/environment assumption used in the cost model, not evidence that the application needs 80 GB. The HA database plan costs twice the standard plan and adds a standby in another Availability Zone; it does not provide application VM or API high availability. Lightsail managed PostgreSQL automatically retains point-in-time recovery data for seven days; restoring creates a **new** database. Deleting the source database deletes its automatic backup records and removes point-in-time recovery. Manual snapshots remain until deleted and currently cost $0.05/GB-month, so retention beyond seven days and recovery after deletion need an explicit snapshot policy.

Use private database networking: AWS documents that a private Lightsail database is accessible only to Lightsail resources in the same account and region via the internal network. PostgreSQL connections must use TLS with certificate verification (`sslmode=verify-full`) and the appropriate AWS CA bundle; the application must manage the database password as a secret.

The local Compose and CI database currently use PostgreSQL 17.6, while AWS's current Lightsail documentation lists PostgreSQL 12–16, and PostgreSQL 12 is no longer available for new Lightsail databases. Do not treat Lightsail managed PostgreSQL as a drop-in for the current local database. Select an available major version only after review and test the application, generated SQL, clean/upgrade migrations, constraints, and runtime behavior against that exact version. Confirm selected plans and PostgreSQL version availability in `ap-southeast-2` during a future approved design review.

## DSQL compatibility and integration gate

The current backend has not been validated against Aurora DSQL. Repository inspection found that the persisted PostgreSQL `ARRAY` facilities column and emitted Alembic index DDL require changes or a DSQL-specific migration path. The current SQLAlchemy engine also uses the standard psycopg dialect; AWS's SQLAlchemy DSQL dialect/connector and IAM token lifecycle are not configured. See the matrix and gated runbook in [dsql-compatibility-validation.md](dsql-compatibility-validation.md).

Before confirming DSQL, inspect the actual schema, repositories and migrations; adapt where needed; then run a clean migration, an upgrade migration, and the existing repository integration journey against a separately approved DSQL test cluster. The validation must cover search filters/count/pagination, favourites idempotency, duplicate review rejection, contribution/report persistence, referential integrity, rating aggregation, concurrent writes/conflict retries, connection refresh, and measured query DPUs. Local PostgreSQL passing is not evidence of DSQL compatibility. No DSQL cluster was created or queried for this proposal because no resource/cost approval was granted.

If these compatibility blockers are material, compare RDS for PostgreSQL and encrypted Lightsail managed PostgreSQL on Sydney pricing, database HA, backup/restore, connectivity, and the existing application's PostgreSQL fit before changing the human's preferred direction.

## Deployment, data and observability boundaries

- Treat Lightsail instances and containers as replaceable. Keep application state out of the VM filesystem; store uploads in external object storage if/when uploads exist. The current MVP has no uploaded media implementation.
- DSQL data is external to the VM. Separate the dev/prod database endpoints, users/roles and access policies. Define backup retention and complete a restore drill with explicit RPO/RTO before production.
- Keep local Docker Compose wired to its PostgreSQL container by default. Select Aurora DSQL through deployment-specific cloud configuration only after the DSQL adapter, schema/migration path, authentication, retry behavior and recovery gates pass. An Aurora-enabled cloud development environment must be an explicit opt-in in that environment's configuration; never make the local PostgreSQL setting silently resolve to Aurora.
- Lightsail's standard IAM guidance describes EC2 instance profiles for EC2 apps; Lightsail does not expose that EC2 attachment workflow. Do not assume the app can obtain an instance role automatically. Select and validate a short-lived credential/role-assumption design before using DSQL from the VM; never bake static access keys into an image.
- Run Grafana Cloud Free for hosted dashboards/alerts and a lightweight Alloy or OpenTelemetry Collector per environment. Validate combined dev/prod quotas, account region/data residency, labels/cardinality, pipeline failure/no-data alerts, and a secure browser telemetry relay with no private ingestion token in browser code.
- Hosted alert delivery must reach an authenticated receiver that persists and deduplicates incidents before queueing any agent work. A webhook by itself does not launch an agent. Agent hosting and model usage are separate, unpriced follow-up work.
- Build and deploy the same immutable image from dev to prod. Confirm the repository remains public and uses standard GitHub-hosted runners, check artifact/cache usage against account quotas, and recheck current GHCR pricing policy. Identify deploy credentials and rollback path before implementation; private-repository or non-standard runner use may change costs.
