# PawLocal Terraform state rebuild sequence

The current application Terraform root stores development and production resources together. The approved release design uses independent Terraform roots and state keys for development and production. The old shared state must be destroyed through the protected GitHub Actions recovery workflow before either new environment root is applied. No state file is edited or migrated by hand.

## Sequence

1. Review and apply the standalone `infra/terraform/iam-bootstrap` root locally using the operator's local Terraform credentials, with `manage_github_oidc_provider = false` while the legacy root still owns the existing GitHub OIDC provider. This creates the recovery, plan, and apply roles plus the private saved-plan bucket without uploading credentials.
2. Configure repository variables `PAWLOCAL_DEVELOPMENT_TERRAFORM_PLAN_ROLE_ARN`, `PAWLOCAL_PRODUCTION_TERRAFORM_PLAN_ROLE_ARN`, and `PAWLOCAL_TERRAFORM_RECOVERY_PLAN_ROLE_ARN`, plus shared non-secret plan configuration. The plan jobs have no GitHub Environment, so no review can block before the plan is visible. Configure `development-apply` and `production-apply` GitHub Environments with required reviewers, main-only deployment branches, and the matching apply-role ARN in `PAWLOCAL_TERRAFORM_ROLE_ARN`. `terraform-recovery-apply` is not active while the blocker below remains.
3. Dispatch **Terraform legacy state recovery** from `main` only to generate and review a value-free destroy summary. Its plan is transferred through the private S3 plan bucket, bound to repository ID, run/attempt, commit, state key, and SHA-256. The review helper rejects unsupported resources/actions and any attempt to delete the backend bucket. The workflow then deliberately fails closed before any AWS apply.
4. Recovery apply remains blocked until the bootstrap IAM policy passes independent review and the exact legacy live-resource inventory is reconciled with the destroy plan and narrowly scoped permissions. That review must include DSQL deletion protection, S3 object and version cleanup, OIDC ownership, and the Terraform backend boundary. Do not perform a local or GitHub apply while this blocker is unresolved. Once the reviewed design allows recovery, determine whether the legacy OIDC provider is removed; if so, stop GitHub Terraform jobs and locally apply `infra/terraform/iam-bootstrap` with `manage_github_oidc_provider = true` before resuming them.
5. After recovery and bootstrap ownership are independently cleared, dispatch **Terraform development deployment** from `main` with an immutable API image digest. The first apply may create the development CloudFront OAC; the plan reviewer allows OAC creation but rejects updates, replacements, and deletes. Bootstrap starts with selector `oac_create_environment = "development"`, allowing OAC creation only for development (plus temporary read-only Get while the ARN is not yet known); it grants no OAC List, update, or delete.
6. After development apply and the database-backed API check succeed, copy the development `oac_arn` from the workflow summary into the separate local IAM bootstrap configuration. Apply the reviewed bootstrap transition that pins this ARN and sets `oac_create_environment = "production"`. Set repository variable `PAWLOCAL_DEVELOPMENT_OAC_ARN` to the exact ARN. Then dispatch **Terraform production promotion** from `main`, passing the successful development workflow run ID and the same immutable image digest. Its GitHub API preflight verifies the run came from the development workflow, completed successfully from `main`, and used that digest. After assuming the production plan role, a read-only boto3 check fetches the two exact apply roles' inline policies with `iam:GetRolePolicy`; it requires the development policy to pin OAC read/update/delete actions to the recorded development ARN and the initial production policy to allow only OAC create/read actions during the production creation window. This fails closed before Terraform plan if the local bootstrap transition is missing or incorrectly scoped. The production plan is generated first; only its apply job waits for approval in `production-apply`.
7. After production applies, copy its `oac_arn` from the workflow summary into the local bootstrap configuration, pin it, and clear `oac_create_environment`. Set repository variables `PAWLOCAL_DEVELOPMENT_OAC_ARN` and `PAWLOCAL_PRODUCTION_OAC_ARN` to the respective outputs. Each later plan and apply compares its configured ARN with Terraform state and fails closed if absent or mismatched. OAC updates and replacements remain blocked unless a separately reviewed policy refresh and workflow change allows them.

## Approval and execution limits

- No AWS CLI is used. Application infrastructure is managed through Terraform in GitHub Actions. GitHub Actions authenticates through OIDC and uses the AWS SDK helper only for private plan-object transfer. The local Terraform applies described here manage only the separate IAM bootstrap state.
- The public plan summary is generated only for plans marked applyable, complete, and error-free. It omits all values, counts output changes without displaying their values, and rejects deferred or unsupported changes.
- The Terraform backend bucket and the separate IAM bootstrap state are outside the old shared application state. Recovery cannot delete the backend bucket; the recovery plan reviewer fails closed if that bucket is listed for deletion.
- The recovery workflow currently cannot apply. Its explicit blocker prevents AWS credentials and Terraform apply until IAM scope and the exact legacy resource inventory pass independent review.
- GitHub Environment protections are an administrative prerequisite for `development-apply` and `production-apply`. Workflow YAML selects the apply environments, but it cannot enforce required reviewers or deployment branch restrictions by itself. Plan jobs have no Environment boundary and use branch-scoped read-only roles. Recovery apply remains unavailable pending the documented scope review.
- These files describe the reviewed workflow path. They do not claim that AWS resources were destroyed/recreated, that the bootstrap state was applied, that GitHub Environment protections were configured, or that either deployment is live.
