# Architecture

**Status:** The approved source architecture uses S3/CloudFront, Lightsail Container Services, Aurora DSQL and Cognito in matching development/production states, plus the standalone IAM bootstrap state. Earlier “no apply/deployment complete” wording described the Issue #135 implementation baseline, not current live status. Current release/reconciliation evidence is linked from the [configuration inventory](configuration-inventory.md); live readiness must be checked against exact release and approval evidence. Hosted instrumentation, dashboard definitions and the incident controller are implemented; their presence does not establish live acceptance. [Issue #225](https://github.com/alanlima/pawlocal/issues/225) records accepted development correlation and the amended resilience criterion; development alert/G1, production monitoring, repair/G2 and production-origin recovery remain open under [#226](https://github.com/alanlima/pawlocal/issues/226), [#230](https://github.com/alanlima/pawlocal/issues/230), [#229](https://github.com/alanlima/pawlocal/issues/229) and [#231](https://github.com/alanlima/pawlocal/issues/231). Use the [submission readiness tracker](https://github.com/alanlima/pawlocal/issues/281) for dated delivery evidence; [DEC-011](decisions.md#dec-011--hosted-observability-and-minimal-cloud-incident-responder) records the selected design.

The [DEC-018 / #346](decisions.md#dec-018--shared-cloudfront-application-entry-point-346) source design reuses each environment's CloudFront distribution for both frontend and API. Default frontend requests use private S3 and its SPA rewrite; `/api` and `/api/*` use the generated Lightsail HTTPS origin without URI rewriting. Cloud builds bind to the matching frontend origin plus `/api/v1`; public health is `/api/health`, while Lightsail retains internal `/health`. API caching and error TTLs are disabled, and requests forward authorization, queries, bodies and trace headers with the origin Host. Obsolete custom API DNS/certificates are retired by Terraform. This remains subject to reviewed plans and separately authorized runtime verification; the generated Lightsail origin stays public, with additional origin/CORS work tracked by [#417](https://github.com/alanlima/pawlocal/issues/417).

## System shape

```text
React/Vite client ── typed service interface ── mock adapter (Stage 1)
                                            └── HTTP adapter (Stage 3)
                                                      │ OpenAPI
                                                      ▼
                                             FastAPI application
                                      API → use cases → domain rules
                                                      │ repositories
                                                      ▼
                                      PostgreSQL (Stage 3; persistence)

Search → API → database → place details
  └──────── logs, metrics and correlated traces ────────┘
```

## Boundaries and sequence

- The browser owns presentation and client interaction. Feature modules use shared typed services; components do not construct requests.
- Mock and HTTP adapters implement the same service contracts. Stage 1 uses mock data; Stage 3 replaces adapters after the backend/API contract is reviewed.
- FastAPI route handlers handle HTTP concerns only. Application use cases coordinate domain behavior. Domain rules do not depend on FastAPI or SQLAlchemy.
- SQLAlchemy repositories and Alembic migrations live in infrastructure. PostgreSQL is introduced in Stage 3.
- `openapi.yaml` is the shared contract. Contract changes must be reflected in client types, backend schemas, tests and docs.
- Stage 2 local frontend/observability and Stage 3 backend/persistence may start in parallel after their specifications are human-approved and both issues are open. They must use separate branches and Git worktrees because both may edit root Compose configuration.
- Stage 2's monitoring review gate must pass before Stage 3 is considered complete and before Stage 3.1 starts. Stage 3.1 adds browser-to-API-to-database tracing and structured backend logs and reconciles the two Compose stacks; it may proceed in its own coordinated worktree while Stage 3 continues. Stage 3 cannot be marked complete until Stage 3.1 integration and independent review evidence are complete.
- Stage 4 release policy is PR CI, immutable backend image publishing, automatic development deployment after successful main CI, and ordinary manual production promotion gated on successful development verification; DEC-012/#239 adds automatic exact-release incident promotion after machine checks. Promotion reuses the same verified image digest. Issue #75 keeps environment-specific Lightsail Container Services, managed TLS endpoints, Route 53 records, public GHCR digest references, and Terraform-managed deployment versions. Issue #135 changes their ownership: bootstrap owns shared OIDC trust, deployment-role identity, baseline permissions, and boundaries; development and production states each own only their application resources, environment policies, and matching attachments. Cross-environment retagging or updates are not accepted. Terraform alone owns AWS infrastructure lifecycle; CLI use is limited to approved artifact operations and read-only inspection. Each protected environment apply gates Lightsail deployment on a two-phase DSQL setup: the matching apply identity has exact-cluster administrative connection access to verify the application role, singleton runtime mapping, schema, and grants, then assumes only the matching runtime identity to apply and verify the clean application-owned baseline. Terraform records digest triggers and successful execution, not continuous ownership of native catalog objects. Local Docker Compose continues to use PostgreSQL. Hosted telemetry extends this initial release under Issue #59; distinguish implemented configuration from accepted live signals. Backup/HA/recovery remain tracked by Issue #44. Initial billable infrastructure provisioning remains owner-authorized; the activated #239 path permits only machine-validated application-release updates within existing resources. See DEC-007, DEC-008, the [hosting proposal](stage4-hosting-options.md), and [DSQL compatibility review](dsql-compatibility-validation.md).
- Stage 4 identity uses one Terraform-managed Cognito user pool per environment. Both pools use case-insensitive usernames and passwords, open self sign-up, required `name`, no email/phone verification, and MFA off. Only minimum password length and the lowercase, uppercase, and number requirements vary by environment. A pre sign-up Lambda auto-confirms only self-service sign-ups so the user can sign in immediately without a confirmation code or privileged backend call; Cognito does not generally require this Lambda when another confirmation mechanism is used. See [DEC-009](decisions.md) and master [Issue #184](https://github.com/alanlima/pawlocal/issues/184).

## Stage 4 Issue #135 baseline

The former combined roots and workflows are reference material only. The legacy automatic release was fail-closed before the new roots were added; the former combined-state operation and rollback workflows remain inert. The active application entry points are `infra/terraform/environments/development` and `infra/terraform/environments/production`, called through `.github/workflows/terraform-environment.yml`. The existing `infra/terraform/iam-bootstrap` state remains authoritative for shared identity and boundaries.

The final backend keys are `pawlocal/iam-bootstrap/terraform.tfstate`, `pawlocal/development/terraform.tfstate`, and `pawlocal/production/terraform.tfstate`. Application resources begin in clean states; former application resources are never imported. Bootstrap declaratively adopts only the verified development publisher identity and the shared fixed identities selected by explicit reviewed inputs. Environment states own their resources, policies, and matching attachments; the module cannot manage role identity/trust/boundaries. Development must be planned, approved, applied, and verified before production becomes eligible.

Bootstrap permissions boundaries must not depend on generated full resource ARNs. Their write ceilings use a stable ARN for the intended resource family or a deterministic environment/name prefix. `Resource = "*"` is not a substitute for that scope: it is used only where an AWS create action has no resource-level authorization and request-tag conditions constrain it where supported, or for DEC-009's exact regional `logs:DescribeLogGroups` metadata exception. After the first environment apply, exact generated resource ARNs may tighten the environment-owned application, publisher, and runtime policies; effective access remains the intersection of those exact grants and the stable bootstrap boundary, so no bootstrap boundary rewrite is required. Runtime trust remains a separate staged handoff: the generated Lightsail service principal is supplied through an independently reviewed bootstrap plan. A trust principal is not a permissions-boundary resource exception. The DSQL runtime identity and refresh behavior still require live verification. See [DEC-008](decisions.md), the [operator guide](terraform-greenfield-operations.md), and the historical [deployment record](deployment-aws-frontend.md).

For DEC-009, the bootstrap state owns three deterministic roles per environment: a delegated Cognito Terraform plan role, a delegated Cognito Terraform apply role with its own permissions boundary, and the pre-sign-up Lambda execution role. The existing environment plan/apply identities may assume only their exact matching delegated role; they receive no direct Lambda or CloudWatch Logs mutation authority and no direct `iam:PassRole`. The delegated roles trust only the matching existing environment role and never trust GitHub OIDC directly. The delegated plan role is read-only. The delegated apply role has only the exact Lambda/log lifecycle and exact execution-role pass permission conditioned on Lambda as the target service. The execution role trusts only Lambda and writes only to streams under its matching log group. Apart from the approved account-region log-group metadata visibility below, none of these roles may access another environment, Terraform state, saved-plan storage, or Cognito APIs outside its stated responsibility.

Both delegated identity policies, plus the delegated apply permissions boundary, include one dedicated provider-refresh exception: exactly `logs:DescribeLogGroups` on `Resource = "*"`, conditioned by `aws:RequestedRegion` equal to the configured AWS region. AWS does not support resource-level authorization or a resource, tag, or request-prefix condition for this action, so IAM cannot enforce the deterministic `LogGroupNamePrefix` that the provider sends. The accepted consequence is visibility of log-group metadata within the account and configured region. The exception grants no log-content or stream read, including `logs:DescribeLogStreams`, `logs:GetLogEvents`, `logs:FilterLogEvents`, `logs:GetLogRecord`, `logs:GetLogGroupFields`, `logs:StartQuery`, `logs:GetQueryResults`, `logs:StartLiveTail`, and `logs:Unmask`. `logs:ListTagsForResource` and every Logs mutation remain scoped to the exact matching log-group ARN; cross-environment mutation remains prohibited. No Lambda permission uses a wildcard resource.

Environment states own their Cognito pools and dependent clients/domains, Lambda functions and packages, finite-retention log groups, Cognito invoke permissions, environment policies, and matching attachments. Lambda, log-group, and invoke-permission resources use `aws.cognito_deployment`; Cognito and unrelated resources stay on the default provider. The alias selects the temporary shared-config profile `${var.project_name}-cognito-deployment`. Protected workflows set the same validated Terraform project-name input to its approved default, `pawlocal`, and derive `pawlocal-cognito-deployment` from it. Plan and destroy-plan jobs map that profile to the matching delegated read role. Apply, teardown-preparation apply, and destroy-apply jobs map it to the matching delegated write role. The deterministic AWS role names remain `pawlocal-*` under DEC-009. The default provider remains on the existing environment credentials, so workflows must not set a global `AWS_PROFILE`.

The pre-sign-up function uses the official `terraform-aws-modules/lambda/aws` module pinned exactly to [v8.12.0](https://github.com/terraform-aws-modules/terraform-aws-lambda/releases/tag/v8.12.0) with its one-file `source_path`, the existing execution role, and no module-created IAM role or invoke permission. Package identity is source-content-derived, with no run-specific `hash_extra`; `trigger_on_package_timestamp = false` and `ignore_source_code_hash = true` prevent local rebuilds from causing unchanged cloud-code updates. Normal saved plans force replacement only of the module-local `local_file.archive_plan[0]` and `null_resource.archive[0]` resources. This makes the reviewed plan schedule the module's package sidecar and build on the fresh apply runner, including a retry where prior package state exists but a dependent Lambda action remains. The apply runner checks the exact planned commit and a clean tracked tree immediately before applying, so it cannot package modified source. Only the opaque saved plan and metadata cross jobs; no Lambda ZIP is transferred through S3. Teardown preparation uses no forced replacements, so Lambda and its module package state remain unchanged under the existing strict lifecycle guard. Final destroy simply deletes the Lambda, log group, invoke permission, and module packaging state from the reviewed delete-only plan without building, restoring, transferring, or validating a package. Moving an existing run-specific filename to this stable identity can cause one migration code update; subsequent unchanged-source plans must leave Lambda unchanged. Real source changes change the content filename and still deploy; function configuration changes remain managed normally.

The repository currently targets the commercial `aws` partition, as reflected by existing environment-role validation against `arn:aws:iam::...`. With the workflow-local constant `AWS_PARTITION=aws`, each job constructs the delegated role ARN from the existing validated `PAWLOCAL_AWS_ACCOUNT_ID`, exact `development` or `production` environment, and normalized `plan` or `apply` purpose. No new GitHub role-ARN variable is required. The environment Terraform input `cognito_pre_sign_up_role_arn` is nullable and defaults to `null`. When unset, Terraform computes the effective `arn:<current-partition>:iam::<current-account>:role/pawlocal-<environment>-cognito-pre-signup` from its current partition, caller identity, and selected environment; workflows do not export `TF_VAR_cognito_pre_sign_up_role_arn` by default. A non-null override is allowed only for a separately approved need and must validate as that exact execution role in the current partition, account, and environment. Whether defaulted or overridden, the effective ARN remains the only `iam:PassRole` target and cannot broaden delegated apply authority. Bootstrap outputs provide reviewed post-apply evidence that the created ARNs match this contract; workflows do not read them as runtime configuration.

Before writing the temporary shared config, every Terraform job that evaluates or applies an environment root validates the protected 12-digit account ID, selected environment, normalized job purpose, and constructed delegated-role name and ARN. The workflow masks that ARN before later steps, keeps the temporary profile outside the repository, blanks its path and role input from diagnostic steps, and deletes it in an `if: always()` cleanup step. Terraform separately rejects any non-null execution-role override that does not equal the exact current-partition, current-account, matching-environment role before it can affect a plan. Because the delegated hop is role chaining, its maximum session is one hour. Each Terraform operation starts with fresh credentials and must complete within that window; expiry or interruption requires a new saved plan and review.

The Cognito sequencing above originated in [Issue #185](https://github.com/alanlima/pawlocal/issues/185) and the later execution amendment [#192](https://github.com/alanlima/pawlocal/issues/192). Those records and the IAM/application implementations [#186](https://github.com/alanlima/pawlocal/issues/186) / [#187](https://github.com/alanlima/pawlocal/issues/187) are now closed. They preserve design and implementation history; they are not pending dependencies or authorization for a new apply. Future identity changes still require independent review and the applicable exact-plan/owner-approval gates.

## Security and data integrity

Public reads require no account. Write operations require authentication and backend authorization, validation and rate limits. Personal data must be minimized and excluded from telemetry. AI-produced data stays a draft until a human verifies source and factual claims.

## Open decisions

Moderation operations and source provenance schema require review before their respective implementation stages. Stage 3 token validation and reportable-contribution API decisions are recorded in DEC-002 and `openapi.yaml`; the approved Stage 4 Cognito identity lifecycle and delegated Terraform execution amendment are recorded in DEC-009. Issues #185, #192, and #187 do not configure or test self-service password recovery, and users without a verified email address or phone number cannot use `ForgotPassword`. A future recovery policy, account deletion and retention, social federation, sign-up abuse controls, and production deletion protection remain separate decisions. Documentation approval does not authorize provisioning AWS resources.

## Hosted monitoring and incident response

The [hosted observability specification](specs/hosted-observability.md) and [incident responder specification](specs/incident-responder.md) define the selected #59/#42 extension. Their planning-era status banners describe the original scope; current acceptance belongs to the linked GitHub issues above. Implemented sources include `backend/pawlocal/cloud_telemetry.py`, the frontend telemetry integration, six environment-bound dashboard definitions in `observability/grafana/cloud/dashboards/`, and the trusted incident workflows catalogued in [GitHub Actions](github-actions.md). React Faro sends to Grafana's hosted frontend collector; FastAPI sends direct asynchronous OTLP with a server-only credential. Optional Grafana panels query CloudWatch read-only. The independent HMAC-authenticated Lambda Function URL dispatches a fixed GitHub-hosted workflow; cloud agents produce a tested fix PR and independent report. DEC-012/#239 requires trusted automatic squash merge, verified development and automatic exact-release production recovery for the incident MVP. Model jobs hold no merge/release credentials; there is no runtime human approval. One-time protection/model/budget/privacy/provisioning setup remains necessary, and the optional approval switch is deferred.

This explicitly supersedes old relay/backend-intake grooming guidance for the planned hosted extension: there is no custom collector, durable AWS incident queue or added FastAPI webhook in this design. The independent receiver is separate from the application API; accepted dispatch is not proof of completed remediation or recovery. Local Compose collection remains unchanged. Development/production isolation, exact SSM mappings, state/secret ownership, delivery limitations and G1/G2/live gates are detailed in the specs and [implementation plan](plans/monitoring-implementation.md).
