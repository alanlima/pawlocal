## DEC-001 — Stage delivery sequence and parallel workstreams

- **Status:** Approved 2026-10-18.
- **Context:** The human approved the updated Stage 2 and Stage 3 specifications in PR #14. The Codex review identified conflicts with the architecture, implementation plan, and this decision record; this entry makes the approved sequencing consistent across those canonical documents. See [PR #14 review comment](https://github.com/alanlima/pawlocal/pull/14#discussion_r4304401902).
- **Decision:** Complete Foundations and Stage 1 in order. After human approval of both workstream specifications and with both issues open, Stage 2 local frontend/observability and Stage 3 backend/persistence may proceed in parallel in separate branches and Git worktrees. Stage 2 review is required before Stage 3.1 starts. After that review, Stage 3.1 may proceed in its own coordinated worktree while Stage 3 continues. Stage 3 cannot be marked complete until the Stage 2 review gate passes and Stage 3.1 cross-layer instrumentation, combined Compose integration, and review evidence are complete.
- **Consequence:** Stage 2 and Stage 3 can be implemented concurrently without sharing working directories. Stage 3.1 integrates their Compose changes and verifies the combined stack. No stage gate or required review is waived; Stage 3 completion remains dependent on Stage 3.1 evidence.

## DEC-002 — Stage 3 identity token validation and reportable contributions

- **Status:** Approved 2026-10-18.
- **Context:** Stage 3 requires a simple identity validation approach for protected API operations, and the existing frontend report dialog needs a public list of contributions it can target.
- **Decision:** Use Amazon Cognito User Pool as the OIDC identity provider. The API accepts user-pool **access tokens** only, validates the configured exact issuer (`iss`), signature using the pool's published JWKS signing key, `token_use=access`, expiry, and `client_id` against the configured app-client ID. Keep issuer, app-client ID, and any API resource audience externalized in configuration. Cognito access tokens include `aud` only when resource binding is requested: when resource binding is enabled, require and validate the configured API audience; otherwise validate `aud` if present against the configured resource audience. Do not treat an ID token or client-supplied user ID as API authorization. Add an unauthenticated paginated `GET /contributions/reportable` that returns only already-published public fields needed by the report dialog (`id`, `kind`, `body`, `place_id`, `rating`, `created_at`); do not return reporter or contributor identity. No Cognito pool, AWS resource, or production deployment is provisioned as part of this decision.
- **Consequences:** Protected operations use verified token subject as the user identity. Environment configuration and tests must cover issuer, signing key, token purpose, expiry, app client, and optional/resource-bound audience checks. The public listing exposes only published contribution content already intended for public display. See the [Cognito access token claims](https://docs.aws.amazon.com/cognito/latest/developerguide/amazon-cognito-user-pools-using-the-access-token.html), [JWT verification guidance](https://docs.aws.amazon.com/cognito/latest/developerguide/amazon-cognito-user-pools-using-tokens-verifying-a-jwt.html), and [resource binding documentation](https://docs.aws.amazon.com/cognito/latest/developerguide/cognito-user-pools-define-resource-servers.html).

## DEC-003 — MVP discovery taxonomy

- **Status:** Approved 2026-10-18.
- **Context:** Stage 3 requires stable area, category and facility filters; the existing Stage 1 frontend already defines the MVP values.
- **Decision:** Use place categories `dog_park`, `beach`, `walk`, `hiking_area`, and `cafe`; facilities `Fenced`, `Off-leash area`, `Drinking water`, `Shade`, `Picnic tables`, and `Accessible paths`; and curated, human-readable South East Queensland area labels. Current UI examples are `Brisbane City`, `Brisbane North`, `Gold Coast`, `Moreton Bay`, and `Sunshine Coast`, but the list is not exhaustive. Filter areas by exact label; they are not precise geospatial boundaries. Unknown or unverified access/facility facts remain absent/unknown and must never be inferred.
- **Consequences:** Stage 3 API, persistence and adapters must use the category/facility enums and exact-match area-label semantics. The broader freshness and verification policy remains open. See the approved [product taxonomy](../product-spec.md#approved-mvp-discovery-taxonomy) and `openapi.yaml`.

## DEC-005 — Full-stack AWS MVP hosting and release

- **Status:** Approved 2026-10-19.
- **Context:** Issue #43 implements the budget-approved full-stack AWS MVP. The owner selected AWS Lightsail for the FastAPI container and Aurora DSQL in Sydney for cloud persistence. Local Docker Compose remains on PostgreSQL. Runtime implementation and offline compatibility checks exist, but no DSQL cluster has been provisioned or tested.
- **Decision:** Use Lightsail + Aurora DSQL for the Issue #43 MVP. Keep Compose/PostgreSQL as the local workflow and require explicit environment configuration for cloud DSQL; never silently switch providers. Use a separate AWS IAM user's long-term access key for each dev/prod environment, supplied to the application through a root-owned restricted runtime credentials file and the standard AWS SDK credentials chain (for example, `AWS_SHARED_CREDENTIALS_FILE`). Do not place key material in repository files, images, user data, database URLs, or logs. Revisit shorter-lived identity alternatives after MVP deployment under [Issue #63](https://github.com/alanlima/pawlocal/issues/63).
- **Issue #43 release policy:** Pull requests run relevant checks. After a successful merge to `main` and passing CI, publish an immutable backend image and deploy the verified release automatically to development. Production promotion is a separate manually dispatched workflow that selects a release verified in development and promotes the same backend image digest. Production deploys do not run automatically on merge. Keep public frontend configuration environment-specific and free of secrets. Workflow code is in `.github/workflows/fullstack-release.yml` and `.github/workflows/deploy-production.yml`; passing PR checks do not establish a cloud deployment.
- **MVP scope:** Keep telemetry disabled for the initial release; telemetry enablement and provider/data-residency decisions remain for later review in [Issue #59](https://github.com/alanlima/pawlocal/issues/59). Backup, HA, restore, RPO/RTO, and recovery work are excluded and deferred to [Issue #44](https://github.com/alanlima/pawlocal/issues/44), for review after the MVP is deployed to cloud. They are not MVP deployment gates.
- **Implementation and validation status:** The backend has an Aurora DSQL SQLAlchemy engine path using the AWS DSQL connector and SDK credential chain, a separate DSQL clean-install baseline/runner, normalized facility schema and compatible search queries, bounded pre-commit OCC retry, reserved `admin` rejection, and an early guard preventing generic PostgreSQL Alembic revisions from running against DSQL. PostgreSQL CI and offline DSQL lint/compile/fake-engine checks pass. Live DSQL migration, connection/token refresh, runtime credential-file behavior on Lightsail, and OCC behavior remain unverified. The clean-install baseline supports an empty cloud database only; PostgreSQL data import is not implemented. Issue #62 Terraform creates the scoped IAM application users/policies but does not create DSQL custom database roles or access-key material; a separately controlled role bootstrap and environment key delivery are required before runtime validation. Adapter verification includes a public `/places` database-query smoke, which does not prove authenticated create/read persistence; that live-development gate remains open until a Cognito test identity exists. CloudTrail can store `DbConnect` security audit events; the notification destination and S3 retention period are unset, and the current bucket has no lifecycle expiration. See the [DSQL compatibility review](dsql-compatibility-validation.md) and [costed plan](stage4-hosting-options.md).
- **Consequence:** The cloud provider path is selected, while its live runtime validation and deployment remain outstanding. Continue with the approved Lightsail/DSQL adapter and dev/prod targets under Issue #62; do not replace the selected database without an owner decision. The MVP budget approval does not include telemetry or Issue #44 recovery/HA work.

## DEC-004 — Static frontend AWS delivery

- **Status:** Approved 2026-10-18 for the initial Stage 4 frontend release.
- **Context:** PawLocal can publish a mock-backed React/Vite bundle without deploying the API or database. The public repository must remain reusable and contain no owner-specific DNS name, hosted-zone ID, AWS account ID, or credentials.
- **Decision:** Serve the initial static frontend from a private S3 bucket through CloudFront with OAC, HTTPS via an existing ACM wildcard certificate supplied as an input, SPA route fallback, and Route 53 alias records for the parameterized `pawlocal.<domain>` hostname. The build sets `VITE_USE_MOCK_BACKEND=true`. Store Terraform state in the pre-existing, versioned and encrypted state bucket under key `pawlocal/terraform.tfstate`; inject the bucket name through local backend configuration. The current GitHub Actions workflow deploys on `main` pushes that change `frontend/**` and authenticates with a branch-restricted OIDC role.
- **Scope boundary:** This remains the approved initial mock-backed static site only. It does not approve a development distribution, `pawlocal-dev.<domain>` DNS, API/database hosting, or the Issue #43 full-stack CI/CD promotion design. Any change from the current static-site production workflow to automatic dev deployment plus manual production promotion requires separate targets and credentials, use of the owner-approved MVP budget, and explicit provisioning approval as described in DEC-005 and Issue #43.
- **Consequences:** Review CloudFront/data-transfer and S3 costs before apply. This decision covers only the static frontend; it does not select hosting for the backend, database, or observability. See [the deployment runbook](deployment-aws-frontend.md).
