## DEC-002 — Stage 3 identity token validation and reportable contributions

- **Status:** Approved 2026-10-18.
- **Context:** Stage 3 requires a simple identity validation approach for protected API operations, and the existing frontend report dialog needs a public list of contributions it can target.
- **Decision:** Use Amazon Cognito User Pool as the OIDC identity provider. The API accepts user-pool **access tokens** only, validates the configured exact issuer (`iss`), signature using the pool's published JWKS signing key, `token_use=access`, expiry, and `client_id` against the configured app-client ID. Keep issuer, app-client ID, and any API resource audience externalized in configuration. Cognito access tokens include `aud` only when resource binding is requested: when resource binding is enabled, require and validate the configured API audience; otherwise validate `aud` if present against the configured resource audience. Do not treat an ID token or client-supplied user ID as API authorization. Add an unauthenticated paginated `GET /contributions/reportable` that returns only already-published public fields needed by the report dialog (`id`, `kind`, `body`, `place_id`, `rating`, `created_at`); do not return reporter or contributor identity. No Cognito pool, AWS resource, or production deployment is provisioned as part of this decision.
- **Consequences:** Protected operations use verified token subject as the user identity. Environment configuration and tests must cover issuer, signing key, token purpose, expiry, app client, and optional/resource-bound audience checks. The public listing exposes only published contribution content already intended for public display. See the [Cognito access token claims](https://docs.aws.amazon.com/cognito/latest/developerguide/amazon-cognito-user-pools-using-the-access-token.html), [JWT verification guidance](https://docs.aws.amazon.com/cognito/latest/developerguide/amazon-cognito-user-pools-using-tokens-verifying-a-jwt.html), and [resource binding documentation](https://docs.aws.amazon.com/cognito/latest/developerguide/cognito-user-pools-define-resource-servers.html).

## DRAFT-009 — GitHub-only sign-in through Cognito

- **Status:** Proposed 2026-10-22 for owner review under [Issue #110](https://github.com/alanlima/pawlocal/issues/110). This draft is not approved, does not authorize implementation or provisioning, and does not change Issue #110's acceptance criteria.
- **Context:** PawLocal currently uses a Cognito user pool as the issuer of access tokens accepted by the API under DEC-002. The deployed browser client supports the local `COGNITO` identity provider, while Issue #110 requests GitHub as the only sign-in provider and prohibits a PawLocal username/password path. Amazon Cognito's native social providers are Facebook, Google, Login with Amazon, and Sign in with Apple; other federation must use SAML 2.0 or OpenID Connect (OIDC). A Cognito OIDC provider must supply OIDC discovery or equivalent endpoints, signing keys, and an ID token. GitHub's documented user-login flow is OAuth 2.0 authorization code exchange followed by an API request with an opaque access token; it is not an OIDC identity-provider flow. Configuring GitHub's OAuth endpoints as a Cognito OIDC provider would therefore not satisfy Cognito's protocol requirements. See the [Cognito provider types](https://docs.aws.amazon.com/cognito-user-identity-pools/latest/APIReference/API_ProviderDescription.html), [Cognito OIDC requirements](https://docs.aws.amazon.com/cognito/latest/developerguide/cognito-user-pools-oidc-idp.html), and [GitHub OAuth web flow](https://docs.github.com/en/apps/oauth-apps/building-oauth-apps/authorizing-oauth-apps).

### Options considered

| Option | Fit | Material consequences |
|---|---|---|
| Configure GitHub directly as Cognito OIDC | Rejected as technically incompatible | GitHub OAuth does not provide the OIDC ID token and issuer/JWKS contract Cognito requires. Endpoint substitution would be an unverified protocol shim, not direct federation. |
| Authenticate directly with GitHub in PawLocal and replace Cognito tokens | Not recommended for Issue #110 | This can use GitHub OAuth, but it replaces DEC-002's Cognito-issued access-token contract, requires a new PawLocal session/token authority, and is outside the issue's “through Cognito” scope. |
| Build an AWS-hosted GitHub OAuth-to-OIDC or Cognito custom-auth bridge | Viable but not recommended for the MVP | It retains AWS control but makes PawLocal responsible for security-critical OAuth exchange, token issuance or custom-auth challenges, signing-key rotation, discovery/JWKS availability, abuse controls, and additional AWS runtime permissions and cost. Cognito documents that ordinary federated users sign in through hosted authorization endpoints; custom authentication would be a separate, bespoke security design. |
| Use a standards-compliant OIDC broker between GitHub and Cognito | Recommended, pending owner approval | The broker performs GitHub OAuth and emits a stable OIDC identity to Cognito. Cognito remains PawLocal's token issuer, preserving DEC-002 and the existing frontend/backend token boundary. This adds an external security/data processor, provider configuration, credentials, availability dependency, and potentially recurring cost. |

### Proposed decision

Use one owner-selected, standards-compliant OIDC broker between GitHub and each PawLocal Cognito user pool. GitHub remains the only user-facing sign-in method. Cognito continues to issue the access, ID, and refresh tokens; the API continues to accept only Cognito access tokens as specified by DEC-002. Configure the browser client to support only the broker IdP, omit `COGNITO`, disable public local-user signup and password authentication flows for that client, and pass the broker identity-provider name to Cognito's authorization endpoint so the PawLocal sign-in action redirects directly to GitHub without presenting a local Cognito login form. Anonymous discovery remains unchanged.

This proposal does not select or approve a broker. Before approval, the owner must select a provider and review its hosting location, privacy terms, data retention, availability, export/exit path, free-tier limits, and expected development and production cost. A provider choice is an architectural and data-processing decision, not a routine implementation detail.

### Identity and data handling

- The broker subject must be derived from GitHub's immutable numeric user ID, never the mutable GitHub login, display name, or email address. The broker must emit the same non-reassignable subject on every authentication. Cognito's resulting federated profile and Cognito `sub` remain the application identity used for favourites, contributions, ratings, and reports.
- Do not automatically merge accounts by email or GitHub login. A username change must not create a new PawLocal identity. Any future account-linking or migration workflow requires a separate reviewed decision.
- Request only the GitHub access needed to establish identity. The proposed default is public identity with no repository or organization scopes and no private-email scope. PawLocal does not need email for authorization. If the selected broker cannot produce a compliant stable subject without `read:user`, or the owner requires a verified contact address, document the exact additional scope and consent impact before approval. Adding `user:email` is not implicit in this proposal.
- Store only the stable provider subject and the minimum display attributes needed by the product. Do not persist the GitHub OAuth access token in PawLocal or expose it to the browser, API logs, traces, Terraform output, or deployment evidence. The broker's retention of GitHub tokens and profile data must be part of the provider review.
- GitHub owns credential recovery and MFA. PawLocal provides no password reset or recovery path. Loss or revocation of the GitHub identity prevents new PawLocal sign-in. Self-service PawLocal account deletion and contribution-retention behavior remain outside Issue #110 and require a separate product decision; this draft does not silently define or implement them.

### Session, logout, and revocation

- A successful sign-in returns through Cognito's existing authorization-code-with-PKCE callback. Cancellation, denied consent, invalid state, provider failure, and incomplete token exchange return the user safely to anonymous browsing with a clear, non-sensitive error.
- Sign-out must revoke the PawLocal Cognito refresh token where supported, clear the tab session, and use the Cognito logout endpoint. It ends the PawLocal and Cognito session; it must not claim to sign the user out of GitHub globally. A later sign-in may reuse an active GitHub or broker session unless the selected provider supports an approved account-selection prompt.
- Revoking the GitHub authorization does not by itself invalidate an active broker session or an already-issued Cognito token. The selected broker must document when it revalidates GitHub authorization and how an operator terminates its sessions. Keep the Cognito access-token lifetime bounded, revoke the refresh token on PawLocal sign-out, and document an operator procedure for disabling a compromised federated Cognito profile. Changing token lifetimes or adding global-session revocation requires security review and tests.

### Secret lifecycle and Terraform ownership

- Use separate GitHub registrations and broker/Cognito clients for development and production so callbacks, credentials, consent, rotation, and incident containment cannot cross environments. Register only the exact Cognito `/oauth2/idpresponse` callback and approved sign-out/callback URLs.
- Never commit OAuth client secrets, store them in ordinary Terraform variables, place them in Terraform state or saved plans, expose them as outputs, or print them in Actions logs. Marking a Terraform value `sensitive` only redacts presentation; it does not keep the value out of state.
- Treat the two credential relationships separately. The GitHub OAuth client secret is consumed by the broker and must remain in the broker's audited secret store; it does not enter PawLocal AWS or Terraform. The OIDC client secret that Cognito uses with the broker is the AWS-side secret addressed by the following no-state design. Provider onboarding must document secret custody and rotation without publishing either value.
- The normal `aws_cognito_identity_provider.provider_details` map includes `client_secret`, so it does not by itself prove compliance with the no-state-secret requirement. The recommended implementation direction is a Terraform-owned AWS Secrets Manager secret populated through Terraform's ephemeral input and `secret_string_wo` support, combined with a Terraform-owned CloudFormation identity-provider resource that consumes a Secrets Manager dynamic reference. Terraform and CloudFormation documentation state that write-only values are omitted from plan/state and that the resolved dynamic-reference value is not persisted in the template or CloudFormation logs. This direction must first pass an isolated proof against the repository's exact saved-plan transfer workflow; if the same reviewed plan cannot be applied without persisting or re-planning the value, stop and return to the owner. See [Terraform write-only arguments](https://developer.hashicorp.com/terraform/language/manage-sensitive-data/write-only), [Secrets Manager write-only values](https://registry.terraform.io/providers/hashicorp/aws/latest/docs/resources/secretsmanager_secret_version), and [CloudFormation Secrets Manager dynamic references](https://docs.aws.amazon.com/AWSCloudFormation/latest/UserGuide/dynamic-references-secretsmanager.html).
- Keep the source secret in protected environment secret storage and make it available only to the approved plan/apply jobs that require it. Rotation creates a new provider credential, writes a new secret version through the same no-state path, forces the identity-provider update without exposing the value, verifies development sign-in, and only then revokes the old credential. Record version counters and verification, never values.
- Cognito, secret metadata/value ownership, CloudFormation identity-provider configuration, and any required execution role remain Terraform-owned in the matching approved state boundaries. No console, AWS CLI, SDK, shell script, or untracked post-apply mutation may configure the Cognito provider or AWS secret.

### AWS permissions and cost

- Bootstrap must add only the permissions needed for the chosen no-state design to its environment-specific boundary. The environment-owned policy must grant the exact matching Cognito identity-provider, Secrets Manager, and CloudFormation operations and resources. A narrowly scoped CloudFormation execution role, if required, belongs to the IAM bootstrap state; the environment state may pass only that exact role and manage only its matching stack. Cross-environment secret access, broad `GetSecretValue`, arbitrary `iam:PassRole`, and wildcard stack management are prohibited.
- The recommended design adds one Secrets Manager secret and one small CloudFormation stack per environment, plus the selected broker. CloudFormation has no additional service charge, while Secrets Manager charges per secret and API call. The current public example price is USD $0.40 per secret-month and $0.05 per 10,000 API calls, so secret storage is approximately USD $0.40/month for development or $0.80/month for development and production before tax, broker charges, and Cognito usage. Reconfirm regional pricing before apply. Cognito currently lists a 50-MAU monthly free tier for OIDC-federated users and USD $0.015 per MAU above it; confirm the pool tier and current pricing before approval. See [Secrets Manager pricing](https://aws.amazon.com/secrets-manager/pricing/) and [Cognito pricing](https://aws.amazon.com/cognito/pricing/).
- Do not add NAT gateways, load balancers, always-on broker compute, or production resources under this draft. A self-hosted broker requires a new cost and security decision.
