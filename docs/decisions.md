- **Status:** Approved 2026-10-18.

The Codex review identified conflicts with the architecture, implementation plan, and this decision record; this entry makes the approved sequencing consistent across those canonical documents. - **Decision:** Complete Foundations and Stage 1 in order. ## DEC-002 — Stage 3 identity token validation and reportable contributions

- **Status:** Approved 2026-10-18.
- **Context:** Stage 3 requires a simple identity validation approach for protected API operations, and the existing frontend report dialog needs a public list of contributions it can target.
- **Decision:** Use Amazon Cognito User Pool as the OIDC identity provider. The API accepts user-pool **access tokens** only, validates the configured exact issuer (`iss`), signature using the pool's published JWKS signing key, `token_use=access`, expiry, and `client_id` against the configured app-client ID. Keep issuer, app-client ID, and any API resource audience externalized in configuration. Cognito access tokens include `aud` only when resource binding is requested: when resource binding is enabled, require and validate the configured API audience; otherwise validate `aud` if present against the configured resource audience. Do not treat an ID token or client-supplied user ID as API authorization. Add an unauthenticated paginated `GET /contributions/reportable` that returns only already-published public fields needed by the report dialog (`id`, `kind`, `body`, `place_id`, `rating`, `created_at`); do not return reporter or contributor identity. No Cognito pool, AWS resource, or production deployment is provisioned as part of this decision.
- **Consequences:** Protected operations use verified token subject as the user identity. Environment configuration and tests must cover issuer, signing key, token purpose, expiry, app client, and optional/resource-bound audience checks. The public listing exposes only published contribution content already intended for public display. See the [Cognito access token claims](https://docs.aws.amazon.com/cognito/latest/developerguide/amazon-cognito-user-pools-using-the-access-token.html), [JWT verification guidance](https://docs.aws.amazon.com/cognito/latest/developerguide/amazon-cognito-user-pools-using-tokens-verifying-a-jwt.html), and [resource binding documentation](https://docs.aws.amazon.com/cognito/latest/developerguide/cognito-user-pools-define-resource-servers.html).

## DEC-003 — MVP discovery taxonomy

- **Status:** Approved 2026-10-18.
- **Context:** Stage 3 requires stable area, category and facility filters; the existing Stage 1 frontend already defines the MVP values.
- **Decision:** Use place categories `dog_park`, `beach`, `walk`, `hiking_area`, and `cafe`; facilities `Fenced`, `Off-leash area`, `Drinking water`, `Shade`, `Picnic tables`, and `Accessible paths`; and curated, human-readable South East Queensland area labels. Current UI examples are `Brisbane City`, `Brisbane North`, `Gold Coast`, `Moreton Bay`, and `Sunshine Coast`, but the list is not exhaustive. Filter areas by exact label; they are not precise geospatial boundaries. Unknown or unverified access/facility facts remain absent/unknown and must never be inferred.
- **Consequences:** Stage 3 API, persistence and adapters must use the category/facility enums and exact-match area-label semantics. The broader freshness and verification policy remains open. See the approved [product taxonomy](../product-spec.md#approved-mvp-discovery-taxonomy) and `openapi.yaml`.

## DEC-005 — Full-stack AWS MVP hosting and release

- **Status:** Approved 2026-10-19.
- **Context:** Issue #43 implements the budget-approved full-stack AWS MVP. The owner selected AWS Lightsail for the FastAPI container and Aurora DSQL in Sydney for cloud persistence. Local Docker Compose remains on PostgreSQL. Runtime implementation and offline compatibility checks exist, but no DSQL cluster has been provisioned or tested.
- **Decision:** Use Lightsail + Aurora DSQL for the Issue #43 MVP. Keep Compose/PostgreSQL as the local workflow and require explicit environment configuration for cloud DSQL; never silently switch providers. The owner approved one-off AWS CLI access-key creation only after Terraform creates each app IAM user, plus storing each value in the corresponding GitHub environment secrets and a Desktop TXT file. Keys are not Terraform inputs/outputs, state, plans, repository files, images, user data, database URLs, or logs. The deployment adapter receives these environment-scoped credentials over SSH stdin and installs them as root-owned runtime credentials on the matching Lightsail host; Terraform manages the host configuration and IAM users/policies but never key material. The apply that provisions the users remains gated on a merged and reviewed Terraform change and a fresh integrated plan.
- **Issue #43 release policy:** Pull requests run relevant checks. After a successful merge to `main` and passing CI, publish an immutable backend image and deploy the verified release automatically to development. Production promotion is a separate manually dispatched workflow that selects a release verified in development and promotes the same backend image digest. Production deploys do not run automatically on merge. Keep public frontend configuration environment-specific and free of secrets. Workflow code is in `.github/workflows/fullstack-release.yml` and `.github/workflows/deploy-production.yml`; passing PR checks do not establish a cloud deployment.
- **MVP scope:** Keep telemetry disabled for the initial release; telemetry enablement and provider/data-residency decisions remain for later review in [Issue #59](https://github.com/alanlima/pawlocal/issues/59). Backup, HA, restore, RPO/RTO, and recovery work are excluded and deferred to [Issue #44](https://github.com/alanlima/pawlocal/issues/44), for review after the MVP is deployed to cloud. They are not MVP deployment gates.
- **Implementation and validation status:** The backend has an Aurora DSQL SQLAlchemy engine path using the AWS DSQL connector and SDK credential chain, a separate DSQL clean-install baseline/runner, normalized facility schema and compatible search queries, bounded pre-commit OCC retry, reserved `admin` rejection, and an early guard preventing generic PostgreSQL Alembic revisions from running against DSQL. The Terraform candidate adds environment-specific Cognito pools/clients, DSQL schema-role setup, Lightsail, DNS, and deployment configuration. PostgreSQL CI and offline DSQL lint/compile/fake-engine checks pass. No DSQL cluster has been live validated, and no Terraform apply, app key, deployment, or seed has occurred. The clean-install baseline supports an empty cloud database only; PostgreSQL data import is not implemented. Issue #62 Terraform creates scoped IAM application users and policies; the separately authorized one-off CLI key creation is still pending those Terraform-managed principals. Adapter verification includes a public `/places` database-query smoke, which does not prove authenticated create/read persistence; that live-development gate remains open until tested against the deployed Cognito user pool. CloudTrail can store `DbConnect` security audit events; the notification destination and S3 retention period are unset, and the current bucket has no lifecycle expiration. See the [DSQL compatibility review](dsql-compatibility-validation.md) and [costed plan](stage4-hosting-options.md).
- **Consequence:** The cloud provider path is selected, while its live runtime validation and deployment remain outstanding. Continue with the approved Lightsail/DSQL adapter and dev/prod targets under Issue #62; do not replace the selected database without an owner decision. The MVP budget approval does not include telemetry or Issue #44 recovery/HA work.

## DEC-004 — Static frontend AWS delivery

- **Status:** Approved 2026-10-18 for the initial Stage 4 frontend release.
- **Context:** PawLocal can publish a mock-backed React/Vite bundle without deploying the API or database. The public repository must remain reusable and contain no owner-specific DNS name, hosted-zone ID, AWS account ID, or credentials.
- **Decision:** Serve the initial static frontend from a private S3 bucket through CloudFront with OAC, HTTPS via an existing ACM wildcard certificate supplied as an input, SPA route fallback, and Route 53 alias records for the parameterized `pawlocal.<domain>` hostname. The build sets `VITE_USE_MOCK_BACKEND=true`. Store Terraform state in the pre-existing, versioned and encrypted state bucket under key `pawlocal/terraform.tfstate`; inject the bucket name through local backend configuration. The current GitHub Actions workflow deploys on `main` pushes that change `frontend/**` and authenticates with a branch-restricted OIDC role.
- **Scope boundary:** This remains the approved initial mock-backed static site only. It does not approve a development distribution, `pawlocal-dev.<domain>` DNS, API/database hosting, or the Issue #43 full-stack CI/CD promotion design. Any change from the current static-site production workflow to automatic dev deployment plus manual production promotion requires separate targets and credentials, use of the owner-approved MVP budget, and explicit provisioning approval as described in DEC-005 and Issue #43.
- **Consequences:** Review CloudFront/data-transfer and S3 costs before apply. This decision covers only the static frontend; it does not select hosting for the backend, database, or observability. See [the deployment runbook](deployment-aws-frontend.md).

## DRAFT-006 — Terraform ownership for the full-stack AWS MVP

- **Status:** Proposed 2026-10-19; awaiting owner review. No AWS resources or Terraform state have been changed under this proposal.
- **Context:** The existing root Terraform state at `pawlocal/terraform.tfstate` owns the live production frontend bucket, CloudFront distribution, and `pawlocal.alanlima.cloud` DNS aliases. The first Issue #62 implementation used a separate Terraform root that proposed a second production bucket/distribution and duplicate DNS aliases. The owner requires Terraform to be the only mechanism for infrastructure changes and the authoritative state to remain intact.
- **Proposed decision:** Preserve the existing root Terraform state and resource addresses as the sole owner of production frontend resources and the already state-managed account GitHub OIDC provider. Compose the full-stack resources into the existing root configuration through a child module with no independent backend. Create development-only frontend bucket, CloudFront distribution, and DNS resources in the child module. Reuse the current production frontend bucket/distribution for production asset promotion. Keep the production CloudFront distribution frontend-only. Route `api.pawlocal.<domain>` directly to the production Lightsail static IP through a Terraform-managed Route 53 A record; development uses `api-dev.<domain>`. TLS is provided by Caddy on each API host. Do not route API traffic through either frontend distribution. Do not use manual state commands or edits to change ownership; only reviewed Terraform configuration, including `moved` blocks, may update Terraform addresses. All AWS infrastructure resource creation, configuration, and deletion must be performed through reviewed Terraform configuration and its intended state; no console, AWS CLI, or script may mutate infrastructure.
- **Consequences:** Production infrastructure remains in one state without duplicate CloudFront aliases. The integrated root plan preserves the existing production CloudFront distribution as frontend-only and adds API DNS records to the API hosts. The deployment adapter may publish application artifacts and request a cache invalidation, but may not provision or modify AWS infrastructure resources. This proposal does not authorize an apply, DNS cutover, or any other AWS mutation.
- **PR #64 implementation status:** The implementation composes `infra/terraform/fullstack` as a child module of the existing `infra/terraform` root (no child backend). Its frontend bucket/distribution/DNS and frontend publish role are development-only. The root retains existing production S3, CloudFront, DNS, and OIDC resource ownership. Both frontend CloudFront distributions serve only frontend content. Terraform manages dedicated API A records (`api-dev` and `api`) to the Lightsail static IPs; API HTTPS is terminated by Caddy. Root outputs expose existing production targets alongside development targets. No state operation or AWS API mutation has been performed. The decision remains proposed pending owner review and an integrated root plan review.
- **Deployment runner implementation:** Protected development and production deployment jobs use ephemeral AWS CodeBuild GitHub Actions runners. Terraform creates a GitHub App CodeConnection in `PENDING` state first; after owner authorization in AWS, a separate reviewed Terraform change enables the runner project, webhook, VPC, private subnet, single NAT instance and EIP. The EIP `/32` joins the restricted owner-configured administrator CIDRs for Lightsail SSH. PR and test jobs remain on GitHub-hosted runners. `PAWLOCAL_DEPLOY_MODE=codebuild` gates deploy jobs, and the full-stack workflow can be manually dispatched from `main` to rerun development after runner setup. The app deployment role and CodeBuild execution role remain separate; Terraform/app credentials and private keys are not stored in Terraform state.
- **Runner operating cost and scope:** CodeBuild is billed by build minutes; the single NAT instance and its public IPv4/EIP incur ongoing instance, storage, IPv4, and transfer costs while enabled. The NAT instance is a single point of failure for new deployment jobs, with no HA/recovery work in MVP; the application instances are unaffected by runner egress failure. Teardown through Terraform removes the runner, webhook, NAT, and EIP and returns Lightsail SSH ingress to administrator CIDRs; the GitHub connection remains until separately removed through Terraform. Before enabling the `aws_codebuild_source_credential` resource, inspect the account for an existing CodeBuild GitHub source credential because that resource is account-level. This branch adds configuration only; no AWS or GitHub resources were created or changed.
- **Inputs still requiring owner choices:** the restricted Lightsail SSH administrator CIDR list is a required input; DSQL audit-event capture defaults off, and enabling it requires an owner-selected destination bucket and positive retention days. An optional alert recipient is also unset. The GitHub CodeConnection authorization and review of any existing account-level CodeBuild source credential must be completed before enabling the runner. Environment-scoped DSQL credentials must be supplied separately as GitHub Actions secrets; they are not Terraform inputs or outputs. The module does not select any of these values.
