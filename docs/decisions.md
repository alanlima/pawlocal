## DEC-002 — Stage 3 identity token validation and reportable contributions

- **Status:** Approved 2026-10-18.
- **Context:** Stage 3 requires a simple identity validation approach for protected API operations, and the existing frontend report dialog needs a public list of contributions it can target.
- **Decision:** Use Amazon Cognito User Pool as the OIDC identity provider. The API accepts user-pool **access tokens** only, validates the configured exact issuer (`iss`), signature using the pool's published JWKS signing key, `token_use=access`, expiry, and `client_id` against the configured app-client ID. Keep issuer, app-client ID, and any API resource audience externalized in configuration. Cognito access tokens include `aud` only when resource binding is requested: when resource binding is enabled, require and validate the configured API audience; otherwise validate `aud` if present against the configured resource audience. Do not treat an ID token or client-supplied user ID as API authorization. Add an unauthenticated paginated `GET /contributions/reportable` that returns only already-published public fields needed by the report dialog (`id`, `kind`, `body`, `place_id`, `rating`, `created_at`); do not return reporter or contributor identity. No Cognito pool, AWS resource, or production deployment is provisioned as part of this decision.
- **Consequences:** Protected operations use verified token subject as the user identity. Environment configuration and tests must cover issuer, signing key, token purpose, expiry, app client, and optional/resource-bound audience checks. The public listing exposes only published contribution content already intended for public display. See the [Cognito access token claims](https://docs.aws.amazon.com/cognito/latest/developerguide/amazon-cognito-user-pools-using-the-access-token.html), [JWT verification guidance](https://docs.aws.amazon.com/cognito/latest/developerguide/amazon-cognito-user-pools-using-tokens-verifying-a-jwt.html), and [resource binding documentation](https://docs.aws.amazon.com/cognito/latest/developerguide/cognito-user-pools-define-resource-servers.html).

## DEC-003 — MVP discovery taxonomy

- **Status:** Approved 2026-10-18.
- **Context:** Stage 3 requires stable area, category and facility filters; the existing Stage 1 frontend already defines the MVP values.
- **Decision:** Use place categories `dog_park`, `beach`, `walk`, `hiking_area`, and `cafe`; facilities `Fenced`, `Off-leash area`, `Drinking water`, `Shade`, `Picnic tables`, and `Accessible paths`; and curated, human-readable South East Queensland area labels. Current UI examples are `Brisbane City`, `Brisbane North`, `Gold Coast`, `Moreton Bay`, and `Sunshine Coast`, but the list is not exhaustive. Filter areas by exact label; they are not precise geospatial boundaries. Unknown or unverified access/facility facts remain absent/unknown and must never be inferred.
- **Consequences:** Stage 3 API, persistence and adapters must use the category/facility enums and exact-match area-label semantics. The broader freshness and verification policy remains open. See the approved [product taxonomy](../product-spec.md#approved-mvp-discovery-taxonomy) and `openapi.yaml`.

- **Status:** Open; human direction recorded 2026-10-18 and MVP budget approval recorded 2026-10-19. The DSQL production compatibility and credential path remain unvalidated.
- **Context:** The static frontend hosting choice is recorded in DEC-004. In the review outcome on [Issue #41](https://github.com/alanlima/pawlocal/issues/41), the human selected AWS Lightsail as the application-hosting direction, requested investigation of Aurora DSQL as the preferred cloud database candidate, separate dev/prod environments, and promotion of one tested artifact. Local Docker Compose continues to use its PostgreSQL service by default. The updated [Stage 4 hosting proposal](stage4-hosting-options.md) and [DSQL compatibility review](dsql-compatibility-validation.md) record costs and material compatibility blockers.
- **Direction under review:** Run FastAPI as a normal container on Lightsail and keep Compose/PostgreSQL as the local workflow. Cloud deployments may target Aurora DSQL in Sydney after compatibility and runtime credential validation; the MVP budget is approved. Cloud development opts into DSQL only through explicit environment-specific configuration. Do not silently redirect local Compose to DSQL. DSQL is not a PostgreSQL drop-in. Exclude DynamoDB and Lambda from this decision. Existing S3/CloudFront frontend remains the baseline.
- **Issue #43 release policy (workflow implementation present):** Pull requests run the relevant checks. After a successful merge to `main` and passing CI, the full-stack workflow publishes an immutable backend image and automatically deploys the verified release to development. Production promotion is a separate manually dispatched workflow that selects a release commit verified in development, validates that release and promotes the same backend image digest. Production deploys are not triggered automatically by merges. The frontends are built with environment-specific public settings from the same commit; browser assets contain no secrets. The control flow is implemented in `.github/workflows/fullstack-release.yml` and `.github/workflows/deploy-production.yml`; on [PR #61 head `57df341`](https://github.com/alanlima/pawlocal/pull/61/commits/57df34182b96e9bdbeab96abe55ce1aead1f90fd), the standalone and full-stack CI jobs, workflow validation and GitGuardian passed, while image publication/deployment jobs were skipped as expected for a pull request. No cloud deployment is established by those checks.
- **MVP scope and safeguards:** Keep telemetry disabled. Use separate GitHub `development` and `production` environments, least-privilege short-lived AWS OIDC credentials where supported, production concurrency with `cancel-in-progress: false`, verified CI/dev deployment evidence, health/smoke checks, and immutable artifact identifiers. Application release rollback, database backup/restore, HA, RPO/RTO objectives, and recovery drills are excluded from the MVP and deferred to [Issue #44](https://github.com/alanlima/pawlocal/issues/44), which starts after development and production are deployed.
- **Decision still needed:** Complete DSQL compatibility and runtime credential validation before selecting it for deployment. If material blockers remain, compare the validated RDS for PostgreSQL and encrypted Lightsail managed PostgreSQL alternatives and return the provider decision to the human. The owner has approved the MVP budget; this does not approve later telemetry or deferred backup/HA/recovery spending. Hosted telemetry provider and data residency remain in [Issue #59](https://github.com/alanlima/pawlocal/issues/59).
- **Approved investigation addendum (2026-10-19; scope limited to Issue #53):** The human authorized an isolated, no-AWS prototype and its tests/documentation described in [Issue #53](https://github.com/alanlima/pawlocal/issues/53). ## DEC-004 — Static frontend AWS delivery

- **Status:** Approved 2026-10-18 for the initial Stage 4 frontend release.
- **Context:** PawLocal can publish a mock-backed React/Vite bundle without deploying the API or database. The public repository must remain reusable and contain no owner-specific DNS name, hosted-zone ID, AWS account ID, or credentials.
- **Decision:** Serve the initial static frontend from a private S3 bucket through CloudFront with OAC, HTTPS via an existing ACM wildcard certificate supplied as an input, SPA route fallback, and Route 53 alias records for the parameterized `pawlocal.<domain>` hostname. The build sets `VITE_USE_MOCK_BACKEND=true`. Store Terraform state in the pre-existing, versioned and encrypted state bucket under key `pawlocal/terraform.tfstate`; inject the bucket name through local backend configuration. The current GitHub Actions workflow deploys on `main` pushes that change `frontend/**` and authenticates with a branch-restricted OIDC role.
- **Scope boundary:** This remains the approved initial mock-backed static site only. It does not approve a development distribution, `pawlocal-dev.<domain>` DNS, API/database hosting, or the Issue #43 full-stack CI/CD promotion design. Any change from the current static-site production workflow to automatic dev deployment plus manual production promotion requires separate targets and credentials, use of the owner-approved MVP budget, and explicit provisioning approval as described in DRAFT-002 and Issue #43.
- **Consequences:** Review CloudFront/data-transfer and S3 costs before apply. This decision covers only the static frontend; it does not select hosting for the backend, database, or observability. See [the deployment runbook](deployment-aws-frontend.md).
