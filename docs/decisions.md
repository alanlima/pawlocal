## DEC-002 — Stage 3 identity token validation and reportable contributions

- **Status:** Approved 2026-10-18.
- **Context:** Stage 3 requires a simple identity validation approach for protected API operations, and the existing frontend report dialog needs a public list of contributions it can target.
- **Decision:** Use Amazon Cognito User Pool as the OIDC identity provider. The API accepts user-pool **access tokens** only, validates the configured exact issuer (`iss`), signature using the pool's published JWKS signing key, `token_use=access`, expiry, and `client_id` against the configured app-client ID. Keep issuer, app-client ID, and any API resource audience externalized in configuration. Cognito access tokens include `aud` only when resource binding is requested: when resource binding is enabled, require and validate the configured API audience; otherwise validate `aud` if present against the configured resource audience. Do not treat an ID token or client-supplied user ID as API authorization. Add an unauthenticated paginated `GET /contributions/reportable` that returns only already-published public fields needed by the report dialog (`id`, `kind`, `body`, `place_id`, `rating`, `created_at`); do not return reporter or contributor identity. No Cognito pool, AWS resource, or production deployment is provisioned as part of this decision.
- **Consequences:** Protected operations use verified token subject as the user identity. Environment configuration and tests must cover issuer, signing key, token purpose, expiry, app client, and optional/resource-bound audience checks. The public listing exposes only published contribution content already intended for public display. See the [Cognito access token claims](https://docs.aws.amazon.com/cognito/latest/developerguide/amazon-cognito-user-pools-using-the-access-token.html), [JWT verification guidance](https://docs.aws.amazon.com/cognito/latest/developerguide/amazon-cognito-user-pools-using-tokens-verifying-a-jwt.html), and [resource binding documentation](https://docs.aws.amazon.com/cognito/latest/developerguide/cognito-user-pools-define-resource-servers.html).

## DEC-004 — Static frontend AWS delivery

- **Status:** Approved 2026-10-18 for the initial Stage 4 frontend release.
- **Context:** PawLocal can publish a mock-backed React/Vite bundle without deploying the API or database. The public repository must remain reusable and contain no owner-specific DNS name, hosted-zone ID, AWS account ID, or credentials.
- **Decision:** Serve the initial static frontend from a private S3 bucket through CloudFront with OAC, HTTPS via an existing ACM wildcard certificate supplied as an input, SPA route fallback, and Route 53 alias records for the parameterized `pawlocal.<domain>` hostname. The build sets `VITE_USE_MOCK_BACKEND=true`. Store Terraform state in the pre-existing, versioned and encrypted state bucket under key `pawlocal/terraform.tfstate`; inject the bucket name through local backend configuration. It does not approve a development distribution, `pawlocal-dev.<domain>` DNS, API/database hosting, or the Issue #43 full-stack CI/CD promotion design. Any change from the current static-site production workflow to automatic dev deployment plus manual production promotion requires separate targets and credentials, use of the owner-approved MVP budget, and explicit provisioning approval as described in DEC-005 and Issue #43.
- **Consequences:** Review CloudFront/data-transfer and S3 costs before apply. This decision covers only the static frontend; it does not select hosting for the backend, database, or observability. See [the deployment runbook](deployment-aws-frontend.md).

## DRAFT-006 — Terraform ownership for the full-stack AWS MVP

- **Status:** Superseded by DEC-007 on 2026-10-19. DEC-008 further supersedes the shared-root preservation clause while retaining Terraform-exclusive infrastructure ownership.
- **Context:** The existing root Terraform state at `pawlocal/terraform.tfstate` owns the live production frontend bucket, CloudFront distribution, and `pawlocal.alanlima.cloud` DNS aliases. The first Issue #62 implementation used a separate Terraform root that proposed a second production bucket/distribution and duplicate DNS aliases. The owner requires Terraform to be the only mechanism for infrastructure changes and the authoritative state to remain intact.
- **Proposed decision:** Preserve the existing root Terraform state and resource addresses as the sole owner of production frontend resources and the already state-managed account GitHub OIDC provider. Compose the full-stack resources into the existing root configuration through a child module with no independent backend. Create development-only frontend bucket, CloudFront distribution, and DNS resources in the child module. Reuse the current production frontend bucket/distribution for production asset promotion. Keep the production CloudFront distribution frontend-only. Route `api.pawlocal.<domain>` directly to the production Lightsail static IP through a Terraform-managed Route 53 A record; development uses `api-dev.<domain>`. TLS is provided by Caddy on each API host. Do not route API traffic through either frontend distribution. Do not use manual state commands or edits to change ownership; only reviewed Terraform configuration, including `moved` blocks, may update Terraform addresses. All AWS infrastructure resource creation, configuration, and deletion must be performed through reviewed Terraform configuration and its intended state; no console, AWS CLI, or script may mutate infrastructure.
- **Consequences:** Production infrastructure remains in one state without duplicate CloudFront aliases. The integrated root plan preserves the existing production CloudFront distribution as frontend-only and adds API DNS records to the API hosts. The deployment adapter may publish application artifacts and request a cache invalidation, but may not provision or modify AWS infrastructure resources. This proposal does not authorize an apply, DNS cutover, or any other AWS mutation.
- **PR #64 implementation status:** The implementation composes `infra/terraform/fullstack` as a child module of the existing `infra/terraform` root (no child backend). Its frontend bucket/distribution/DNS and frontend publish role are development-only. The root retains existing production S3, CloudFront, DNS, and OIDC resource ownership. Both frontend CloudFront distributions serve only frontend content. Terraform manages dedicated API A records (`api-dev` and `api`) to the Lightsail static IPs; API HTTPS is terminated by Caddy. Root outputs expose existing production targets alongside development targets. No state operation or AWS API mutation has been performed. The decision remains proposed pending owner review and an integrated root plan review.
- **Inputs still requiring owner choices:** the restricted Lightsail SSH source CIDR list is a required input; DSQL audit-event capture defaults off, and enabling it requires an owner-selected destination bucket and positive retention days. An optional alert recipient is also unset. Environment-scoped DSQL credentials must be supplied separately as local environment variables or GitHub Actions secrets; they are not Terraform inputs or outputs. The module does not select any of these values.

## DEC-008 — Clean Terraform states and bootstrap-owned deployment identity

- **Status:** Approved 2026-10-21 through [Issue #135](https://github.com/alanlima/pawlocal/issues/135).
- **Context:** Issue #135 records a greenfield application-state design and says the former application resources were purged, but the final destroy run was only partially successful and [PR #134](https://github.com/alanlima/pawlocal/pull/134) remains open. Treat the live AWS inventory and remote-state contents as unverified until fresh read-only inspection confirms them. The issue expects only the GitHub deployment IAM identity to carry forward, but its exact role objects, trust, policies, attachments, permissions boundaries, and current Terraform ownership must be verified before adoption. DEC-007 selected the service architecture but assumed preservation of an existing shared application state; that ownership layout is no longer valid.
- **Decision:** Build the accepted PawLocal architecture from clean application state boundaries: a standalone IAM bootstrap state plus separate development and production application states. Bootstrap exclusively owns shared GitHub OIDC trust, deployment role identity, baseline permissions, and permissions boundaries. Each environment state owns only its application resources, its environment-specific managed policy, and the attachment of that policy to its matching bootstrap-owned deployment role. Neither environment may manage role identity, trust, baseline permissions, boundaries, or the other environment's resources. Do not migrate or import former application resources.
- **Existing-role adoption:** Read-only AWS and Terraform inspection must first identify the exact existing GitHub deployment IAM resources and prove they are not already owned by another active state. Only those verified identity resources may be adopted into the bootstrap state. The import must be represented in reviewed Terraform configuration and visible in a saved plan that shows no duplicate ownership, unintended replacement, or deletion. Manual state editing, `state mv`, `state rm`, and ad hoc imports are prohibited.
- **Survivor cleanup:** If inspection finds application resources or legacy state bindings, block the affected environment and record exact identifiers, ownership, cost exposure, and name-collision risk. Cleanup must be a separately scoped, owner-approved, independently reviewed Terraform change with a fresh saved plan. Do not import survivors into the new bootstrap, development, or production states. If an orphan can be removed only after temporary Terraform adoption, first amend Issue #135 and this decision to authorize that cleanup-only exception. No affected environment plan may proceed until verification shows no duplicate ownership or collision remains.
- **Isolation:** The cross-environment CloudFront retag-and-update risk previously accepted for the draft split-state work is superseded and is not permitted by Issue #135. Environment policy and attachment ownership must prevent one environment from retagging, attaching to, or changing the other environment's resources. DEC-009 records the sole approved visibility exception: regional `logs:DescribeLogGroups` exposes account-region log-group metadata but no content or cross-environment mutation. Any other AWS authorization limitation that prevents strict isolation must stop and return the design conflict to the owner.
- **Execution boundary:** The owner-authorized local Terraform exception applies only to the isolated bootstrap state, using higher-permission credentials from the operator environment or credential provider and an independently reviewed saved plan. Development and production infrastructure plans and applies run only through GitHub Actions, the matching protected Environment approval, and application of the exact reviewed saved plan. Credentials must not enter repository files, Terraform inputs, state, plans, logs, or artifacts.
- **Preserved decisions and gates:** DEC-007's Lightsail Container Services, Aurora DSQL, S3/CloudFront frontends, Route 53 routing, immutable container releases, telemetry-disabled initial release, and development-before-production promotion remain accepted. Issue #135 does not approve new services, telemetry, backup/HA/recovery work, or a hosting change. Fresh cost/provisioning approval, live DSQL validation, independent review, and the applicable deployment gates remain mandatory before application apply or release.
- **Documentation consequence:** References to the former combined root, shared application state, deployment adapter, migration plan, or previously deployed application resources are historical and non-actionable. [PR #113](https://github.com/alanlima/pawlocal/pull/113), [PR #88](https://github.com/alanlima/pawlocal/pull/88), and [PR #74](https://github.com/alanlima/pawlocal/pull/74) implement earlier ownership or ingress approaches and are reference-only pending explicit disposition; do not merge, close, or use them as Issue #135 implementation instructions. Exact root paths, backend keys, workflow names, outputs, GitHub variables, adapter contract, and operator commands must be documented only after their implementation exists and has been verified.

## DEC-009 — Environment-specific Cognito password authentication

- **Status:** Approved 2026-10-22 through [Issue #184](https://github.com/alanlima/pawlocal/issues/184); delegated Terraform execution amendment approved 2026-10-22 and tracked by [Issue #192](https://github.com/alanlima/pawlocal/issues/192).
- **Context:** DEC-002 selected an Amazon Cognito user pool as the token issuer but did not define the hosted identity lifecycle. GitHub social sign-in was considered and rejected because direct GitHub federation is not supported by Cognito's OIDC identity-provider integration. The owner instead selected Cognito-native username and password authentication. Ordinary Cognito self-sign-up does not make a user immediately eligible to sign in unless the user is confirmed. A Lambda is not a general Cognito requirement: confirmation can use a verification code or a trusted `AdminConfirmSignUp` caller. Neither alternative matches the approved open sign-up flow, which has no email or phone verification and must permit immediate sign-in.
- **Decision:** Terraform provisions one user pool per environment with username-only sign-in, case-insensitive usernames, open self sign-up, the required mutable standard `name` attribute, no email or phone auto-verification, and MFA off. The shared module accepts a password-policy object containing only `minimum_length`, `require_lowercase`, `require_uppercase`, and `require_numbers`, validated with a minimum-length range of 6 through 99. Development supplies `8 / false / false / false`; production supplies `12 / true / true / true`. Symbols are disabled in both environments, and all settings outside the four policy inputs are identical.
- **Confirmation mechanism:** Each pool uses a pre sign-up Lambda. It sets `autoConfirmUser = true` only when `triggerSource` is `PreSignUp_SignUp`, returns every other trigger source unchanged, and does not log event or profile data. This provides immediate confirmation without a code or a privileged backend confirmation call. Cognito ignores auto-confirm responses for administrator-created users, so they retain the normal temporary-password and `FORCE_CHANGE_PASSWORD` lifecycle.
- **Clean-state creation and replacement risk:** Username sign-in options, required attributes, and username case sensitivity must be selected when a pool is created. Under Issue #135, the first development and production plans must create new pools from clean application states; no existing pool replacement is expected or authorized by this decision. The owner accepts that changing these creation-time settings on a later, still-empty pool can require replacement of the pool and dependent clients or domains. There are currently no users, so this work includes no user migration or user-data recovery. Any plan that instead discovers an existing pool, state binding, or other survivor must stop at the Issue #135 inventory gate for separately approved Terraform-only cleanup.
- **Delegated Terraform execution:** The existing environment plan and apply roles do not receive direct Lambda or CloudWatch Logs mutation authority or direct `iam:PassRole`. For each environment, the bootstrap state owns `pawlocal-<environment>-cognito-terraform-plan`, `pawlocal-<environment>-cognito-terraform-apply`, and `pawlocal-<environment>-cognito-pre-signup`. The delegated plan role trusts only the matching existing environment plan role and is read-only. The delegated apply role trusts only the matching existing environment apply role, has its own bootstrap-owned permissions boundary, and receives only the exact matching Lambda and log-group lifecycle plus `iam:PassRole` for the exact execution role when `iam:PassedToService` is `lambda.amazonaws.com`. Neither delegated Terraform role trusts GitHub OIDC directly, accesses Terraform state or saved-plan storage, manages Cognito pools, reads log content, or performs cross-environment mutations. The execution role trusts only `lambda.amazonaws.com` and writes only beneath `/aws/lambda/pawlocal-<environment>-cognito-pre-signup`.
- **CloudWatch Logs metadata exception:** The owner accepts account-region log-group metadata visibility required by the provider. The delegated plan identity policy, delegated apply identity policy, and delegated apply permissions boundary each contain a dedicated statement whose only action is `logs:DescribeLogGroups`, whose resource is `*`, and whose `aws:RequestedRegion` must equal the configured AWS region. Do not broaden it to `logs:Describe*` or `logs:*`. The provider supplies the deterministic matching `LogGroupNamePrefix`, but IAM offers no resource, tag, or request-prefix condition that can enforce that request parameter. The exception does not allow `logs:DescribeLogStreams`, `logs:GetLogEvents`, `logs:FilterLogEvents`, `logs:GetLogRecord`, `logs:GetLogGroupFields`, `logs:StartQuery`, `logs:GetQueryResults`, `logs:StartLiveTail`, or `logs:Unmask`. `logs:ListTagsForResource` and every Logs mutation remain limited to the exact matching log-group ARN, so no cross-environment mutation is allowed. No Lambda action receives an analogous wildcard resource.
- **Provider and workflow contract:** Environment roots expose `aws.cognito_deployment` with shared-config profile `${var.project_name}-cognito-deployment`. Protected workflows set the same validated Terraform `project_name` input to its approved default `pawlocal`, derive `pawlocal-cognito-deployment` from it, and never accept a separate profile-name variable. Plan and destroy-plan jobs map that profile to the matching delegated read role; apply, teardown-preparation apply, and destroy-apply jobs map it to the matching delegated write role. The deterministic AWS role names remain fixed as `pawlocal-*`. The repository currently targets the commercial `aws` partition, consistent with its existing `arn:aws:iam::...` environment-role validation. Each job constructs `arn:${AWS_PARTITION}:iam::<PAWLOCAL_AWS_ACCOUNT_ID>:role/pawlocal-<environment>-cognito-terraform-<purpose>` with the workflow-local constant `AWS_PARTITION=aws`; `<environment>` is exactly `development` or `production`, and `<purpose>` is normalized to `plan` or `apply` from the job lifecycle. No new GitHub role-ARN variable is used. The nullable Terraform input `cognito_pre_sign_up_role_arn` defaults to `null`; when unset, Terraform computes `arn:<current-partition>:iam::<current-account>:role/pawlocal-<environment>-cognito-pre-signup` from the provider partition, caller identity, and selected environment. Workflows do not set `TF_VAR_cognito_pre_sign_up_role_arn` by default. A non-null override requires separate approval and must validate as that exact role in the current partition, account, and environment. The resulting default or validated override remains the sole `iam:PassRole` resource and cannot broaden the delegated apply role. Bootstrap role-ARN outputs remain post-apply verification evidence, not runtime configuration. Before writing the temporary config, the job validates the project name, account, environment, normalized purpose, and constructed delegated role name and ARN. It masks and blanks the delegated identifier from diagnostics and removes the project-derived temporary config in an `if: always()` step. The default provider retains the existing environment credentials, and workflows do not set a global `AWS_PROFILE`. The delegated hop is role chaining and is limited to one hour. Each Terraform operation must start with fresh credentials and complete inside that session; expiry or interruption requires a newly generated and reviewed saved plan.
- **Ownership and delivery:** [Issue #185](https://github.com/alanlima/pawlocal/issues/185) remains closed as the earlier product-design record. [Issue #192](https://github.com/alanlima/pawlocal/issues/192) records this later execution amendment and must merge before implementation resumes. [Issue #186](https://github.com/alanlima/pawlocal/issues/186) owns the bootstrap roles, trust, delegated apply boundaries, exact policies, and outputs. [Issue #187](https://github.com/alanlima/pawlocal/issues/187) owns the environment-state user pools, clients and domains, Lambda package and function, finite-retention log groups, Cognito invoke permissions, provider alias, and workflow mapping; it creates no IAM roles. The function package uses the official `terraform-aws-modules/lambda/aws` module pinned exactly to v8.12.0 with `source_path`, the bootstrap-owned execution role, no module-created role, and no custom package transfer. Normal saved plans use a trusted plan-unique `hash_extra` and apply only from the exact clean planned commit. Teardown preparation reuses the state-recorded build identifier so Lambda is unchanged; final destroy only deletes the function and environment-owned supporting resources and performs no package-specific work. Issues #186 and #187 may develop in parallel only after #192 merges, but #186 must pass its tests, fresh independent review, GitHub Codex review, and saved-plan review where available, then merge before #187 can complete or merge. The bootstrap roles must also be applied through a separately reviewed and explicitly owner-approved bootstrap plan before any live environment plan can use them. This decision does not authorize any Terraform apply.
- **Scope boundary and consequences:** Cognito remains the only supported identity provider. Social providers, database or data-layer changes, user migration, self-service password recovery, sign-up CAPTCHA or rate limiting, and deletion protection or Terraform `prevent_destroy` are excluded. Issues #185, #192, and #187 neither configure an `account_recovery_setting` policy nor test self-service password recovery. Users without a verified email address or phone number cannot use `ForgotPassword`; this is a limitation of the approved attribute and verification choices, not a claim that Terraform configures administrator-only recovery. Any future recovery policy, verification channel, abuse control, deletion protection, or federation requires a separate reviewed decision.
- **Sources:** [Cognito sign-up and confirmation](https://docs.aws.amazon.com/cognito/latest/developerguide/signing-up-users-in-your-app.html), [pre sign-up Lambda trigger](https://docs.aws.amazon.com/cognito/latest/developerguide/user-pool-lambda-pre-sign-up.html), [updating user-pool configuration](https://docs.aws.amazon.com/cognito/latest/developerguide/cognito-user-pool-updating.html), and [password policies and recovery](https://docs.aws.amazon.com/cognito/latest/developerguide/managing-users-passwords.html).
