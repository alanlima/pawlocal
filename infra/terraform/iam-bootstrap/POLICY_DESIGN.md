# Terraform role policy design

This root owns the shared GitHub OIDC provider, GitHub role identity/trust, baseline permissions, permissions boundaries, runtime identities, and the private saved-plan transfer bucket. Development and production roots own application resources and only their matching managed policies and attachments. Configuration is not evidence of an apply.

## Configuration reader roles

Issue #191 automates exact-plan bootstrap execution through the protected workflow described in [the operator guide](../../../docs/iam-bootstrap-actions.md). The separate `pawlocal-terraform-bootstrap-actions` user, dedicated identity policies and independent boundary are external account-bootstrap prerequisites owned by `alanlima`; the workflow never creates or manages that user. The [setup/policy tool](../../../ops/iam-bootstrap/README.md) scopes its effective permissions to the current bootstrap graph, existing backend key/lock, private plan prefix and exact bootstrap-owned String keys. A dedicated configured-region `ssm:DescribeParameters` metadata exception is required for provider refresh; no application-owned values, history or subtree read is permitted. The same user is used for planning/apply, so the GitHub owner gate controls execution rather than a distinct read-only AWS identity. Changed plans still require independent review and explicit owner approval of the exact saved plan.

The bootstrap state owns one `pawlocal-<environment>-configuration-reader` role per environment and the non-secret `configuration_reader_role_arns` output. Each role trusts only its exact immutable-repository-ID-qualified `<environment>-apply` GitHub OIDC subject with audience `sts.amazonaws.com`; the reconciliation job obtains both this identity and its scoped GitHub credential behind the existing protected apply approval. Initial setup also records the actual role ARN in the matching release Environment. This does not authorize bypassing an Environment reviewer or branch policy.

Each reader grants only `ssm:GetParameter` on the configured account/region `parameter/*`, requiring all three `StringEquals` resource tags: `project=<project_name>`, `environment=<matching environment>`, `configuration-access=github-public`. A newly named public parameter with these tags needs no reader policy edit. The exact producer suffix inventories remain separate and continue restricting Terraform write ownership. No discovery, history, recursive/batch read, state access, mutation, tagging or KMS permission is granted. OIDC trust is unchanged.

These tags are authorization, not descriptive metadata or a substitute for secret classification. Only the existing Terraform-owned public **String** producer blocks opt in; never attach the public tag to SecureString, OTLP/HMAC/App keys or other private values. IAM cannot infer String type from these conditions: applying all three public authorization tags to a secret would be a security defect. Review tag changes as access changes. The reader cannot self-tag.

AWS documents tag conditions on parameter `GetParameter` in its [authorization reference](https://docs.aws.amazon.com/service-authorization/latest/reference/list_ssm.html) and [IAM tag guide](https://docs.aws.amazon.com/systems-manager/latest/userguide/security_iam_service-with-iam.html). Missing resources have no authorization tags and may return `AccessDenied` rather than `ParameterNotFound`; do not mask a denial as absence. #223/#233's requested missing-value warning behavior needs a reviewed existence strategy and live verification before relying on it. This PR adds no metadata exception or secret-reader authority.

## Generated configuration publication

Bootstrap owns its six approved String keys per environment, with the runtime-role key absent until that managed role exists. Each application state owns its 12 application Strings (the two API keys wait for managed API DNS), plus the exact-key configuration policy/attachment. Standard-tier parameters use managed-resource attributes; no secret or SecureString payload enters Terraform. The pinned provider defaults to refusing overwrite when creating a resource, so an existing unmanaged key fails rather than being adopted. Read-only collision/ownership inventory is still required before rollout.

The [AWS provider v6.69.1 parameter implementation](https://github.com/hashicorp/terraform-provider-aws/blob/v6.69.1/internal/service/ssm/parameter.go) uses `PutParameter` for create/update, `GetParameter` and `DescribeParameters` for refresh, `ListTagsForResource`/tag mutations through provider tagging, and `DeleteParameter` for deletion. DEC-010 permits one dedicated metadata-only `ssm:DescribeParameters` wildcard-resource statement conditioned by exact configured `aws:RequestedRegion` in environment Terraform plan/apply identities and their apply boundaries. Its provider `Name Equals` filter is not an IAM isolation guarantee: account-region metadata remains visible. Readers, publishers, runtime and Cognito identities receive no metadata grant. Value/tag reads and application mutations use the exact 12 owned keys; the boundary's `api`, `auth`, and `frontend` component prefixes exclude bootstrap keys and intersect the narrower identity policy. Reader and identity grants permit no parameter history, by-path reads or SSM action wildcards. The sole application apply-boundary compaction exception is documented below.

DEC-010's reviewed compaction keeps both rendered boundaries below 6100 bytes. The pre-206 synthetic fixture and native assertions enumerate every non-SSM literal permission-pair change. The permanent lifecycle amendment adds only `s3:DeleteBucketPolicy` and `dsql:DeleteClusterPolicy` to the existing resource/condition scopes. To preserve the size budget, the redundant S3 object ARN is removed: the existing trailing-star bucket-prefix ARN already matches those object suffixes. Tests enumerate each removed literal pair and prove the same effect/action/conditions still cover it under that existing prefix. Other cross-service ARN/action pairs remain the explicitly enumerated unsupported combinations; no unknown pair is assumed unsupported. Distribution/function/OAC separation stays tested.

Proof references: [IAM resource wildcard expansion, including `/`](https://docs.aws.amazon.com/IAM/latest/UserGuide/reference_policies_elements_resource.html), and supported action/resource types for [CloudFront](https://docs.aws.amazon.com/service-authorization/latest/reference/list_cloudfront.html), [Cognito](https://docs.aws.amazon.com/service-authorization/latest/reference/list_cognito-idp.html), [Lightsail](https://docs.aws.amazon.com/service-authorization/latest/reference/list_lightsail.html), and [DSQL](https://docs.aws.amazon.com/service-authorization/latest/reference/list_dsql.html). The finite test lists every added pair explicitly; it is not a general authorization simulator.

## Environment plan roles

Each plan role trusts only its exact `<environment>-plan` GitHub Environment subject; those Environments are restricted to `main`. It can read the matching state, manage only that state's lock object, perform provider refresh reads, and upload only to `plans/<environment>/`. It has no application-service mutation actions and no IAM write actions.

## Environment apply roles

Each apply role trusts its protected `<environment>-apply` GitHub Environment. The production apply role also trusts exactly `production-destroy-prepare` and `production-destroy`, preserving the two separately protected approvals used by the standard destroy workflow; no development destroy subject is trusted. Bootstrap grants state/plan access and narrowly scoped IAM policy administration so the environment root can create/update its fixed-name application, frontend-publish, and runtime policies. The boundary limits policy and role administration to the matching environment's stable name prefixes. The role's inline identity policy is narrower: it names the exact matching policy ARNs, role ARNs, and `iam:PolicyARN` attachment combinations.

Shared IAM policy, boundary, trust, and attachment construction must be driven from the environment metadata and must not branch on literal environment names to include or omit a required deployment capability. Every environment receives the same required policy families and boundary capabilities, while its ARNs, state key, role names, and OIDC subjects remain exact and isolated. Environment-specific workflow subjects belong in the environment metadata; they do not authorize the other environment or imply that both environments expose the same workflows.

The bootstrap-owned boundary is the effective maximum. It does not allow role creation/deletion, trust changes, permissions-boundary changes, `PassRole`, OIDC changes, another environment's state, policies, attachments, DNS names, or named resources.

## Delegated Cognito provider roles

DEC-009 keeps Lambda and log-group lifecycle outside the already size-constrained environment apply boundary. For each environment, bootstrap owns the following separate roles:

| Role | Exact trust | Maximum authority |
|---|---|---|
| `pawlocal-<environment>-cognito-terraform-plan` | Only the matching `pawlocal-<environment>-terraform-plan` role through `sts:AssumeRole`; no direct GitHub OIDC trust. | Provider reads required to refresh the exact deterministic Lambda function and log group, plus the approved account-region `logs:DescribeLogGroups` metadata exception. No write, permissions-management, state, plan-transfer, Cognito, log-content read, or cross-environment mutation access. |
| `pawlocal-<environment>-cognito-terraform-apply` | Only the matching `pawlocal-<environment>-terraform-apply` role through `sts:AssumeRole`; no direct GitHub OIDC trust. | Exact matching Lambda and log-group lifecycle plus exact-role `iam:PassRole` conditioned on `iam:PassedToService = lambda.amazonaws.com`, together with the approved account-region `logs:DescribeLogGroups` metadata exception. It has its own bootstrap-owned permissions boundary and no state, plan-transfer, Cognito, log-content read, or cross-environment mutation access. |
| `pawlocal-<environment>-cognito-pre-signup` | Only the `lambda.amazonaws.com` service principal. | `logs:CreateLogStream` and `logs:PutLogEvents` only for streams beneath `/aws/lambda/pawlocal-<environment>-cognito-pre-signup`; no Cognito or other application API authority. |

The delegated plan identity policy, delegated apply identity policy, and delegated apply permissions boundary each contain a dedicated Logs metadata statement. Its action list is exactly `logs:DescribeLogGroups`, its resource list is exactly `*`, and its `StringEquals` condition requires `aws:RequestedRegion` to equal the configured AWS region. Do not combine it with another action or broaden it to `logs:Describe*` or `logs:*`. AWS exposes no resource, tag, or request-prefix condition for this action. The provider still supplies the deterministic matching `LogGroupNamePrefix`, but that request parameter cannot be enforced by IAM. The owner explicitly approves the resulting account-region log-group metadata visibility while log-content reads and cross-environment mutations remain prohibited.

That exception grants no log-content or stream read: it excludes `logs:DescribeLogStreams`, `logs:GetLogEvents`, `logs:FilterLogEvents`, `logs:GetLogRecord`, `logs:GetLogGroupFields`, `logs:StartQuery`, `logs:GetQueryResults`, `logs:StartLiveTail`, and `logs:Unmask`. `logs:ListTagsForResource` and every create, tag, update, retention, and delete operation remain in separate exact-resource statements limited to the matching log-group ARN. Cross-environment mutation remains denied. Lambda reads and mutations remain exact-resource; no Lambda statement uses `Resource = "*"`.

The existing environment plan and apply identity policies add only `sts:AssumeRole` for their exact matching delegated role. Their effective permission remains the intersection with their existing controls. They receive no direct Lambda or Logs mutation and no direct `iam:PassRole`; the existing environment apply boundary is neither enlarged for those actions nor weakened to make room for them.

The delegated apply role's identity policy and dedicated boundary must both authorize an operation. Lambda permissions use the deterministic matching function ARN. `lambda:AddPermission` is isolated from general function mutation and additionally requires `lambda:Principal = cognito-idp.amazonaws.com`, so the delegated role cannot grant another service or account invoke access. Apart from the dedicated regional `logs:DescribeLogGroups` statement, CloudWatch Logs permissions use the deterministic matching log-group ARN and required stream suffix. Creation requests require the approved project/environment tags, and follow-on operations remain exact-resource and environment-isolated. The only passable role is the matching pre-sign-up execution role, and only when passed to Lambda. The dedicated boundary is tested independently against the AWS 6,144-byte managed-policy maximum and does not consume space in the existing environment boundary.

The `project_name` input defaults to `pawlocal` in the bootstrap, both application environment roots, and the shared environment module. It accepts 1 through 8 ASCII letters, digits, periods, underscores, or hyphens because the value is rendered repeatedly in the size-constrained IAM policies; the restricted single-byte, JSON-safe alphabet makes length the policy-size bound. The eight-character default exercises that maximum and keeps the existing environment boundary at the repository's 6,100-byte budget and the delegated Cognito boundary below AWS's 6,144-byte limit. The bootstrap AWS provider combines it with `managedby = terraform` as `default_tags` for every taggable bootstrap resource, while each resource declares only its specific `environment` and/or `purpose` additions. Explicit Cognito application tag maps remain necessary because provider defaults do not populate IAM request/resource-tag policy conditions or resources managed by the separate environment states. Every bootstrap and application project-tag condition and application tag map therefore derives from the same input. A deliberate non-default value must be supplied consistently to each state-backed Terraform operation; it needs no GitHub variable. The default output remains unchanged, and DEC-009's deterministic `pawlocal-*` role and application-resource names remain fixed regardless of the tag value.

The narrow proposal gives `TagNewLogGroup` both ARN forms for the same deterministic environment group, retaining only `logs:TagResource`, all six approved request-tag values, and the approved tag-key set. IAM cannot distinguish that complete exact-name tagging request from a standalone request with identical context. The mandatory read-only inventory and clean-state plan gate must reject every exact-name survivor instead of adopting it. Partial post-create tag updates retain existing project/environment ownership checks; retention, deletion, untagging, regional metadata visibility, and log-content permissions are unchanged.

For an unqualified function, `resourceFunctionFlatten` unconditionally calls `findLatestFunctionVersionByName`, whose paginator invokes `ListVersionsByFunction`; both delegated policies therefore grant that action on the exact matching function ARN. AWS lists the `function` resource type for [`ListVersionsByFunction`](https://docs.aws.amazon.com/service-authorization/latest/reference/list_lambda.html#awslambda-ListVersionsByFunction), so no wildcard resource is required. Optional branches for concurrency, code signing mutation, KMS association, log-group deletion protection, durable execution, and Lambda publishing are excluded because Issue #187 does not configure those features.

`DescribeLogGroups` is account/region list authorization and has no resource type in the AWS authorization table, which is why the owner-approved statement requires `Resource = "*"` with the configured-region condition. The provider still supplies the exact prefix. AWS also documents two ARN forms for a log group: most actions use the form ending in `:*`, while `TagResource`, `UntagResource`, and `ListTagsForResource` require the same exact log-group ARN without that suffix. The policies keep both forms deterministic and matching-environment-only. See the [CloudWatch Logs authorization reference](https://docs.aws.amazon.com/service-authorization/latest/reference/list_logs.html) and [LogGroup API ARN guidance](https://docs.aws.amazon.com/AmazonCloudWatchLogs/latest/APIReference/API_LogGroup.html).

Bootstrap exposes `cognito_terraform_role_arns`, keyed by environment and then `plan`/`apply`, and `cognito_pre_sign_up_role_arns`, keyed by environment. These outputs are reviewed post-apply evidence that the created roles match the deterministic contract; environment workflows do not consume them as runtime configuration. Development and production application states own the Lambda package/function, finite-retention log group, Cognito invoke permission, user pool, clients/domains, environment policies, and matching attachments. The delegated roles own no application resource and receive no state access.

The environment root configures `aws.cognito_deployment` with the stable shared-config profile `pawlocal-cognito-deployment`. Workflows create that profile outside the repository with `credential_source = Environment`, the constructed matching role ARN, a purpose-specific session name, and `duration_seconds = 3600`. Plan and destroy-plan jobs normalize their purpose to `plan`; apply, teardown-preparation apply, and destroy-apply jobs normalize it to `apply`. The default provider continues to use the existing environment role, and workflows do not set a global `AWS_PROFILE`.

The repository currently targets the commercial AWS partition: existing workflow identity validation requires `arn:aws:iam::...`. Each job therefore sets the workflow-local constant `AWS_PARTITION=aws`, validates the existing protected `PAWLOCAL_AWS_ACCOUNT_ID` as exactly 12 digits and the selected environment as exactly `development` or `production`, and constructs `pawlocal-<environment>-cognito-terraform-<plan|apply>` plus `arn:${AWS_PARTITION}:iam::<PAWLOCAL_AWS_ACCOUNT_ID>:role/pawlocal-<environment>-cognito-terraform-<plan|apply>`. No new GitHub repository or Environment variable supplies a delegated or execution-role ARN.

Before writing the temporary config, the job validates the normalized purpose and constructed delegated role name and ARN. It masks that ARN before later steps and verifies the delegated caller identity after creating the profile. Diagnostic steps blank the delegated role ARN, `AWS_CONFIG_FILE`, and profile name. A final `if: always()` step deletes the temporary config. Bootstrap outputs are verification evidence only and are never copied into GitHub variables or read by these jobs.

The environment Terraform input `cognito_pre_sign_up_role_arn` is nullable with default `null`. In the default path, Terraform derives the effective ARN from `data.aws_partition.current.partition`, `data.aws_caller_identity.current.account_id`, and the selected environment, with the exact role name `pawlocal-<environment>-cognito-pre-signup`. Workflows do not set `TF_VAR_cognito_pre_sign_up_role_arn` by default. A non-null override is allowed only for a separately approved need and must validate against that exact current-partition, current-account, matching-environment role identity. The effective default or validated override is used consistently as the Lambda execution role and as the sole `iam:PassRole` resource in the delegated apply identity policy and boundary; an override cannot broaden pass-role authority.

The delegated assume-role hop is role chaining and can last no more than one hour. Each Terraform operation starts with fresh credentials and must complete within that window. Expired or interrupted operations fail closed and require a newly generated and reviewed saved plan. See the AWS [role chaining guidance](https://docs.aws.amazon.com/IAM/latest/UserGuide/id_roles.html) and [assume-role credential-provider reference](https://docs.aws.amazon.com/sdkref/latest/guide/feature-assume-role-credentials.html).

Bootstrap boundaries must not depend on generated full resource ARNs. Write ceilings use stable scoped ARNs for the intended resource family or a deterministic environment/name prefix. `Resource = "*"` is reserved for AWS create actions that do not support resource-level authorization and are request-tag constrained wherever supported, plus the separately approved dedicated configured-region `logs:DescribeLogGroups` and `ssm:DescribeParameters` metadata statements above. Exact generated ARNs belong in the narrower environment-owned policies after creation; the intersection keeps effective access exact without rewriting the bootstrap boundary.

AWS limits a managed-policy document to 6,144 non-whitespace bytes. The repository enforces a stricter 6,100-byte budget against each rendered, minified environment apply boundary and verifies the environment-owned application policy against the AWS limit. A synthetic length-equivalent fixture prevents shorter placeholder inputs from hiding the reviewed shape. Both environment boundaries include the matching frontend-object deletion ceiling so bootstrap can support the same Terraform-owned lifecycle without being reapplied in a particular environment order. The exact environment identity policy remains limited to its own named policy and bucket family, and teardown remains default-off in the environment root and protected workflow. The exact environment identity policies still narrow effective administrative connection and role-assumption access to the matching cluster and runtime role. Boundary statements omit non-authorizing SIDs and use read-only service patterns; compact Cognito and Lightsail action families fit the policy-size limit while the matching identity policy retains the exact mutation actions. Post-create mutations use only compatible DSQL cluster, Cognito user-pool, Lightsail certificate, and Lightsail container-service resource families. DSQL and Lightsail retain matching authorization-tag conditions; Cognito's listed user-pool client/domain mutation actions support the user-pool resource type but do not list action-level condition keys. The boundary requires matching project/environment authorization tags where the AWS service supports them, while the environment-owned identity policy requires the approved tag-key set and exact generated resources after handoff. S3 creation additionally requires every metadata tag value in both the create and dependent tag authorization. Effective permissions are always the intersection of the stable boundary and the narrower identity policy.

## Publisher and runtime identities

Bootstrap declaratively imports only the read-only-inventory-verified development publisher role when `import_existing_development_deploy_role=true`. The production publisher is created normally. Both trust only their matching release GitHub Environment and use their matching bootstrap-owned environment boundary. Environment roots create the exact frontend publication policy and attachment after their frontend resources exist.

The three app-specific managed policies present in the populated bootstrap state (development frontend, production frontend, and development runtime) have explicit `removed` blocks with `destroy = true`; the reviewed bootstrap plan must delete exactly those three policies rather than preserve duplicate ownership. The additional `identity_production_runtime` removed address is defensive because that resource existed only on an unapplied change and must be a no-op against the populated state. Bootstrap retains only identity, trust, baseline, boundary, and shared plan-transfer ownership. Environment roots are the sole owners of application, frontend-publish, and runtime policies and matching attachments.

The earlier ownership migration removed the two legacy `environment_service_apply` inline policies and their broad application create/update authority. Application states retain resource ownership and managed create/update policies. The owner-approved permanent lifecycle baseline now independently grants apply roles DNS DELETE only within the configured zone and normalized per-environment frontend/API/validation namespace (A/AAAA/CNAME), `s3:DeleteBucketPolicy` within the existing matching bucket-name family, and `dsql:DeleteClusterPolicy` on matching account/region clusters with project/environment resource tags. These bootstrap-owned inline grants survive application-policy narrowing; the boundary still only limits permission. Route 53 has no record resource-tag authorization, so name/type/action conditions and required context keys enforce its scope. S3 retains its established name-prefix boundary; supported other services keep project/environment tags. The boundary adds only the two missing provider-delete actions, with no broad write wildcard or size-budget increase. No application resource is adopted into bootstrap state, and plan roles gain no mutation permission.

The publisher and runtime boundaries use stable resource families from the first bootstrap plan: the matching environment S3 name prefix, the account CloudFront distribution family with matching resource tags, and the regional account DSQL cluster family with matching resource tags. Development and production runtime roles are still created only after bootstrap receives the exact Lightsail `principal_arn` from the matching foundation output. This is a trust-principal handoff, not a permissions-boundary resource handoff or an exception to the stable-boundary rule. The environment root creates the exact DSQL connection policy and attachment. No generated application resource ARN is an input to a bootstrap-owned boundary.

## Saved plan handling

Plan roles upload opaque plans and metadata only beneath their environment prefix. Apply roles can only read that prefix. Metadata binds the plan SHA-256 to repository ID, commit, run, attempt, environment, state key, and a one-way account/backend/region fingerprint. GitHub summaries contain only resource type/action/count. Raw provider logs, raw plan JSON, plan binaries, Terraform state, credentials, secret values, account identifiers, and resource identifiers are not public evidence.

## Hosted public configuration boundary compaction (#225)

The environment apply boundary uses `ssm:*Parameter` and `ssm:*Tags*` only as a compact maximum-permission ceiling. The official [AWS machine-readable SSM action catalog](https://servicereference.us-east-1.amazonaws.com/v1/ssm/ssm.json), version v1.5, retrieved 23 October 2026, contains 164 actions. Exhaustive case-insensitive matching yields exactly the prior six APIs: `GetParameter`, `PutParameter`, `DeleteParameter`, `AddTagsToResource`, `ListTagsForResource` and `RemoveTagsFromResource`. The snapshot records all names, source SHA256 and provenance at `tests/ci/fixtures/aws-ssm-action-catalog.json`; tests exclude history, batch/by-path, DescribeParameters and resource-policy actions. The separate existing region-conditioned DescribeParameters metadata exception remains unchanged.

The boundary's matching environment public namespaces are `config/api/*`, `config/auth/*`, `config/frontend/*`, `config/g*` and `config/o*`. The latter two deliberately cover broader future public namespace families, including Grafana, observability and oncall. They exclude existing/future bootstrap `iam`, `aws`, `terraform` paths and every `/secrets/` path. No private runtime token/HMAC/App key becomes readable through this boundary. The exact environment identity policies retain literal actions and owned source ARNs, so a resource inside a boundary family is not automatically authorized. The matching delegated receiver writer owns its URL separately; the base identity receives only public collision/refresh reads for that URL.

AWS may add a matching action in a future catalog, or a future public namespace may fall within g*/o*. That can widen the boundary ceiling; it cannot add a literal identity grant by itself. Revalidate the catalog and effective identity intersection before changing APIs/ownership. Do not describe this ceiling as containing only today's Grafana names. Pinned-provider compiled realistic fixtures render 6083 development / 6046 production bytes, below the repository 6100-byte and AWS 6144-byte limits. Independent review recomputed both sizes and catalog equivalence. This is a reviewed code proposal, not live IAM/apply authorization.
