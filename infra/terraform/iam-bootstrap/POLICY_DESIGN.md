# Terraform role policy design

This root owns the shared GitHub OIDC provider, GitHub role identity/trust, baseline permissions, permissions boundaries, runtime identities, and the private saved-plan transfer bucket. Development and production roots own application resources and only their matching managed policies and attachments. Configuration is not evidence of an apply.

## Environment plan roles

Each plan role trusts only its exact `<environment>-plan` GitHub Environment subject; those Environments are restricted to `main`. It can read the matching state, manage only that state's lock object, perform provider refresh reads, and upload only to `plans/<environment>/`. It has no application-service mutation actions and no IAM write actions.

## Environment apply roles

Each apply role trusts its protected `<environment>-apply` GitHub Environment. The production apply role also trusts exactly `production-destroy-prepare` and `production-destroy`, preserving the two separately protected approvals used by the standard destroy workflow; no development destroy subject is trusted. Bootstrap grants state/plan access and narrowly scoped IAM policy administration so the environment root can create/update its fixed-name application, Cognito pre-sign-up deployment, frontend-publish, and runtime policies. The boundary limits policy and role administration to the matching environment's stable name prefixes. The role's inline identity policy is narrower: it names the exact matching policy ARNs, role ARNs, and `iam:PolicyARN` attachment combinations.

Shared IAM policy, boundary, trust, and attachment construction must be driven from the environment metadata and must not branch on literal environment names to include or omit a required deployment capability. Every environment receives the same required policy families and boundary capabilities, while its ARNs, state key, role names, and OIDC subjects remain exact and isolated. Environment-specific workflow subjects belong in the environment metadata; they do not authorize the other environment or imply that both environments expose the same workflows.

The bootstrap-owned boundary is the effective maximum. It does not allow role creation/deletion, trust changes, permissions-boundary changes, OIDC changes, another environment's state, policies, attachments, DNS names, or named resources. Its sole `iam:PassRole` ceiling names the matching pre-sign-up execution role and requires `iam:PassedToService = lambda.amazonaws.com`.

Bootstrap boundaries must not depend on generated full resource ARNs. Write ceilings use stable scoped ARNs for the intended resource family or a deterministic environment/name prefix. `Resource = "*"` is reserved for AWS create actions that do not support resource-level authorization and is request-tag constrained wherever the service supports those conditions. Exact generated ARNs belong in the narrower environment-owned policies after creation; the intersection keeps effective access exact without rewriting the bootstrap boundary.

AWS limits a managed-policy document to 6,144 non-whitespace bytes. The repository enforces a 6,143-byte ceiling against each rendered, minified environment apply boundary and verifies both environment-owned deployment policies against the AWS limit. Both environment boundaries include the matching frontend-object deletion and deterministic pre-sign-up Lambda ceilings so bootstrap can support the same Terraform-owned lifecycle without being reapplied in a particular environment order. Boundary statements omit non-authorizing SIDs, combine only actions whose AWS resource types are disjoint, and use compact action families where the exact environment-owned policy supplies the narrower action list. Create boundaries retain matching `project` and `environment` request/authorization tags; the environment-owned application policy retains the complete metadata tag contract. Effective permissions are always the intersection of the stable boundary and the narrower identity policies.

| Service | Maximum environment authority |
|---|---|
| S3 | `CreateBucket` and its provider-required `TagResource` authorization are restricted to the matching `pawlocal-<environment>-` prefix plus matching project/environment request tags. The environment-owned application policy additionally requires the complete six-key metadata tag payload, so an untagged or partially tagged provider fallback remains denied by the effective intersection. `PutBucketTagging`, configuration mutation, cleanup, and the provider's exact name-scoped pre-tag reads stay inside that stable environment bucket-name family. No broad `s3:Get*` is granted. |
| Aurora DSQL | The boundary admits `CreateCluster` and its dependent `TagResource` only with matching project/environment request and authorization tags. The environment-owned application policy additionally requires the complete eight-key cluster payload, including environment-specific `Name` and fixed database `purpose`. Update/delete/policy actions require matching resource tags. The bootstrap runtime boundary uses the account/region cluster family with matching project/environment tags; the environment-owned runtime policy narrows effective connection access to the exact generated cluster. |
| Lightsail | Tagged container-service and certificate creation includes the dependent `TagResource` authorization. Those dependent checks use AWS's pre-creation `ContainerService/*` and `Certificate/*` resource forms, constrained by matching request and authorization tags plus the approved tag-key set. Update/deployment/delete requires matching resource tags, and `UntagResource` is never granted. Provider create/delete waiters can read the exact operation with `GetOperation`; the plural `GetOperations` remains discovery-only. |
| CloudFront | The stable boundary admits tagged distribution creation, exact-name function management, and post-create ceilings for distributions and OACs. Distribution update/delete uses the account distribution family plus matching project/environment resource tags. The compact OAC action family uses the account OAC family because OAC IDs are generated, their ARNs have no deterministic name segment, and CloudFront exposes no supported OAC tag condition. The environment-owned application policy remains exact-resource and exact-action, so the effective permission after handoff is limited to the matching distribution and OAC. `UntagResource` is never granted. |
| Cognito | Tagged user-pool creation includes the dependent `TagResource` authorization against AWS's required `userpool/*` pre-creation resource form, with matching request and authorization tags. The environment-owned application policy keeps the exact provider mutation list. |
| Lambda and CloudWatch Logs | Function lifecycle and permission-policy changes are bounded to `pawlocal-<environment>-cognito-pre-signup`; log-group lifecycle is bounded to `/aws/lambda/pawlocal-<environment>-cognito-pre-signup`. The environment-owned Cognito deployment policy lists the exact provider actions. `PassRole` names only the matching bootstrap role and only Lambda as the passed-to service. The function role trusts only `lambda.amazonaws.com` and can create streams and put events only beneath the matching log group. |
| Route 53 | Changes are limited to the configured zone, the environment frontend/API/validation names, and A/AAAA/CNAME types. |

The normal workflow plan guard rejects deletes and replacements except the provider's expected immutable Lightsail deployment-version replacement. A future destructive infrastructure change requires separate scope and authorization; the boundary alone is not authorization to apply it.

## Publisher and runtime identities

Bootstrap declaratively imports only the read-only-inventory-verified development publisher role when `import_existing_development_deploy_role=true`. The production publisher is created normally. Both trust only their matching release GitHub Environment and use their matching bootstrap-owned environment boundary. Environment roots create the exact frontend publication policy and attachment after their frontend resources exist.

The three app-specific managed policies present in the populated bootstrap state (development frontend, production frontend, and development runtime) have explicit `removed` blocks with `destroy = true`; the reviewed bootstrap plan must delete exactly those three policies rather than preserve duplicate ownership. The additional `identity_production_runtime` removed address is defensive because that resource existed only on an unapplied change and must be a no-op against the populated state. Bootstrap retains only identity, trust, baseline, boundary, and shared plan-transfer ownership. Environment roots are the sole owners of application, frontend-publish, and runtime policies and matching attachments.

The reviewed bootstrap plan must also delete exactly the two legacy `environment_service_apply` inline role policies. Those deletions intentionally remove the former inline application authority now replaced by bootstrap boundaries and environment-owned policies. The existing development app-role boundary keeps its state-compatible description so the policy updates in place; no other delete or replacement is allowed.

The first bootstrap apply partially completed before the environment apply boundaries were created, and the remote state serial advanced. Its saved plan is stale and must never be retried. Issue #186 intentionally adds two pre-sign-up execution roles and their inline log policies, updates both environment boundaries and Terraform-role inline policies, and exposes the role-ARN map. A fresh normal-refresh bootstrap plan must be independently reviewed against that exact scope. Any import, delete, replacement, application resource, unrelated resource, or additional drift is a hard stop.

The publisher and runtime boundaries use stable resource families from the first bootstrap plan: the matching environment S3 name prefix, the account CloudFront distribution family with matching resource tags, and the regional account DSQL cluster family with matching resource tags. Environment roots create and attach the exact bucket/distribution and cluster policies after those resources exist. Their intersection with the boundary retains exact effective access without requiring a second bootstrap boundary rewrite.

Development and production runtime roles are still created only after bootstrap receives the exact Lightsail `principal_arn` from the matching foundation output. This is a trust-principal handoff, not a permissions-boundary resource handoff or an exception to the stable-boundary rule. The environment root creates the exact DSQL connection policy and attachment. No generated application resource ARN is an input to a bootstrap-owned boundary.

Bootstrap also creates deterministic `pawlocal-<environment>-cognito-pre-signup` execution roles and outputs them through `cognito_pre_sign_up_role_arns`, keyed by `development` and `production`. The matching exact ARN is copied through the protected environment handoff into the required `cognito_pre_sign_up_role_arn` root/module input. Environment roots do not read bootstrap remote state directly and cannot accept the other environment's role ARN.

## Saved plan handling

Plan roles upload opaque plans and metadata only beneath their environment prefix. Apply roles can only read that prefix. Metadata binds the plan SHA-256 to repository ID, commit, run, attempt, environment, state key, and a one-way account/backend/region fingerprint. GitHub summaries contain only resource type/action/count. Raw provider logs, raw plan JSON, plan binaries, Terraform state, credentials, secret values, account identifiers, and resource identifiers are not public evidence.

## Mandatory gates

- Bootstrap changes run locally only after independent review of a fresh exact saved plan and only under the owner's explicit bootstrap authorization.
- Application plans/applies run only through protected GitHub Environments.
- Development verification precedes production eligibility.
- Billable application provisioning still needs explicit cost approval.
- DSQL runtime identity and credential refresh require live development verification before production.
- An unrelated account-level personal workload is out of scope and must not appear in plan changes or evidence.
