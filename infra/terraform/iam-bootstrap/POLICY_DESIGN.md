# Terraform role policy design

This root owns the shared GitHub OIDC provider, GitHub role identity/trust, baseline permissions, permissions boundaries, runtime identities, and the private saved-plan transfer bucket. Development and production roots own application resources and only their matching managed policies and attachments. Configuration is not evidence of an apply.

## Environment plan roles

Each plan role trusts only its exact `<environment>-plan` GitHub Environment subject; those Environments are restricted to `main`. It can read the matching state, manage only that state's lock object, perform provider refresh reads, and upload only to `plans/<environment>/`. It has no application-service mutation actions and no IAM write actions.

## Environment apply roles

Each apply role trusts only its protected `<environment>-apply` GitHub Environment. Bootstrap grants state/plan access and narrowly scoped IAM policy administration so the environment root can create/update its fixed-name application, frontend-publish, and runtime policies. The boundary limits policy and role administration to the matching environment's stable name prefixes. The role's inline identity policy is narrower: it names the three exact policy ARNs, the three exact role ARNs, and the matching exact `iam:PolicyARN` attachment combinations.

The bootstrap-owned boundary is the effective maximum. It does not allow role creation/deletion, trust changes, permissions-boundary changes, `PassRole`, OIDC changes, another environment's state, policies, attachments, DNS names, or named resources.

Bootstrap boundaries must not depend on generated full resource ARNs. Write ceilings use stable scoped ARNs for the intended resource family or a deterministic environment/name prefix. `Resource = "*"` is reserved for AWS create actions that do not support resource-level authorization and is request-tag constrained wherever the service supports those conditions. Exact generated ARNs belong in the narrower environment-owned policies after creation; the intersection keeps effective access exact without rewriting the bootstrap boundary.

AWS limits a managed-policy document to 6,144 non-whitespace bytes. The repository enforces a stricter 6,060-byte budget against each rendered, minified environment apply boundary and verifies the environment-owned application policy against the AWS limit. The reviewed real-input development boundary is 6,040 bytes, leaving 20 bytes to the repository gate and 104 bytes to AWS's limit; a synthetic length-equivalent fixture prevents shorter placeholder inputs from hiding this shape. The previous 5,500-byte target was raised to accommodate the provider's required DSQL create-time authorization for the complete eight-tag cluster payload plus the protected DSQL setup handoff; the exact environment identity policies still narrow effective administrative connection and role-assumption access to the matching cluster and runtime role. Boundary statements omit non-authorizing SIDs and use read-only service patterns; compact Cognito and Lightsail action families fit the policy-size limit while the matching identity policy retains the exact mutation actions. Post-create mutations use only compatible DSQL cluster, Cognito user-pool, Lightsail certificate, and Lightsail container-service resource families. DSQL and Lightsail retain matching authorization-tag conditions; Cognito's listed user-pool client/domain mutation actions support the user-pool resource type but do not list action-level condition keys. The boundary requires matching project/environment authorization tags where the AWS service supports them, while the environment-owned identity policy requires the approved tag-key set and exact generated resources after handoff. S3 creation additionally requires every metadata tag value in both the create and dependent tag authorization. Effective permissions are always the intersection of the stable boundary and the narrower identity policy.

| Service | Maximum environment authority |
|---|---|
| S3 | `CreateBucket` and its provider-required `TagResource` authorization are both restricted to the matching `pawlocal-<environment>-` prefix, exact tag keys, and the complete expected tag values. An untagged provider fallback therefore remains denied. `PutBucketTagging`, configuration mutation, cleanup, and the provider's exact name-scoped pre-tag reads stay inside that stable environment bucket-name family. The environment-owned publisher policy narrows effective object access to the exact generated bucket. No broad `s3:Get*` is granted. |
| Aurora DSQL | Tagged `CreateCluster` and its dependent `TagResource` authorization require the exact eight-key cluster payload: the six common application tags plus the environment-specific `Name` and fixed database `purpose`. A missing, extra, or incorrect tag fails closed. Update/delete/policy actions require matching resource tags. The bootstrap runtime boundary uses the account/region cluster family with matching project/environment tags; the environment-owned runtime policy narrows effective connection access to the exact generated cluster. |
| Lightsail | Tagged container-service and certificate creation includes the dependent `TagResource` authorization. Those dependent checks use AWS's pre-creation `ContainerService/*` and `Certificate/*` resource forms, constrained by matching request and authorization tags plus the approved tag-key set. Update/deployment/delete requires matching resource tags, and `UntagResource` is never granted. Provider create/delete waiters can read the exact operation with `GetOperation`; the plural `GetOperations` remains discovery-only. |
| CloudFront | The stable boundary admits tagged distribution creation, exact-name function management, and separate post-create ceilings for distributions and OACs. Distribution update/delete uses the account distribution family plus matching project/environment resource tags. OAC update/delete uses the account OAC family because OAC IDs are generated, their ARNs have no deterministic name segment, and CloudFront exposes no supported OAC tag condition. The environment-owned application policy remains exact-resource, so the effective permission after handoff is limited to the matching distribution and OAC. Distribution actions and OAC actions never share a statement, and `UntagResource` is never granted. |
| Cognito | Tagged user-pool creation includes the dependent `TagResource` authorization against AWS's required `userpool/*` pre-creation resource form, with matching request tags and absent authorization tags. Follow-on management requires matching resource tags. |
| Route 53 | Changes are limited to the configured zone, the environment frontend/API/validation names, and A/AAAA/CNAME types. |

The normal workflow plan guard rejects deletes and replacements except the provider's expected immutable Lightsail deployment-version replacement. A future destructive infrastructure change requires separate scope and authorization; the boundary alone is not authorization to apply it.

## Publisher and runtime identities

Bootstrap declaratively imports only the read-only-inventory-verified development publisher role when `import_existing_development_deploy_role=true`. The production publisher is created normally. Both trust only their matching release GitHub Environment and use their matching bootstrap-owned environment boundary. Environment roots create the exact frontend publication policy and attachment after their frontend resources exist.

The three app-specific managed policies present in the populated bootstrap state (development frontend, production frontend, and development runtime) have explicit `removed` blocks with `destroy = true`; the reviewed bootstrap plan must delete exactly those three policies rather than preserve duplicate ownership. The additional `identity_production_runtime` removed address is defensive because that resource existed only on an unapplied change and must be a no-op against the populated state. Bootstrap retains only identity, trust, baseline, boundary, and shared plan-transfer ownership. Environment roots are the sole owners of application, frontend-publish, and runtime policies and matching attachments.

The reviewed bootstrap plan must also delete exactly the two legacy `environment_service_apply` inline role policies. Those deletions intentionally remove the former inline application authority now replaced by bootstrap boundaries and environment-owned policies. The existing development app-role boundary keeps its state-compatible description so the policy updates in place; no other delete or replacement is allowed.

The first bootstrap apply partially completed before the environment apply boundaries were created, and the remote state serial advanced. Its saved plan is stale and must never be retried. After the size-safe boundary change is merged, normal refresh should produce only two environment apply-boundary creates and eight dependent environment Terraform role/inline-policy updates. If it contains any import, delete, replacement, application resource, unrelated resource, or additional drift, stop for a new review instead of applying it.

The publisher and runtime boundaries use stable resource families from the first bootstrap plan: the matching environment S3 name prefix, the account CloudFront distribution family with matching resource tags, and the regional account DSQL cluster family with matching resource tags. Environment roots create and attach the exact bucket/distribution and cluster policies after those resources exist. Their intersection with the boundary retains exact effective access without requiring a second bootstrap boundary rewrite.

Development and production runtime roles are still created only after bootstrap receives the exact Lightsail `principal_arn` from the matching foundation output. This is a trust-principal handoff, not a permissions-boundary resource handoff or an exception to the stable-boundary rule. The environment root creates the exact DSQL connection policy and attachment. No generated application resource ARN is an input to a bootstrap-owned boundary.

Each environment also has a dedicated output-reconciliation role trusted only by the matching protected `<environment>-reconcile` GitHub Environment. Its inline policy grants `s3:GetObject` for exactly the bootstrap state and that environment's application state plus `s3:GetBucketLocation`. It has no list, lock, write, Terraform-plan, provider-discovery, or application-resource permissions. This role supports read-only output and state-revision binding; GitHub Environment mutation uses a separately scoped short-lived GitHub App token.

## Saved plan handling

Plan roles upload opaque plans and metadata only beneath their environment prefix. Apply roles can only read that prefix. Metadata binds the plan SHA-256 to repository ID, commit, run, attempt, environment, state key, and a one-way account/backend/region fingerprint. GitHub summaries contain only resource type/action/count. Raw provider logs, raw plan JSON, plan binaries, Terraform state, credentials, secret values, account identifiers, and resource identifiers are not public evidence.

## Mandatory gates

- Bootstrap changes run locally only after independent review of a fresh exact saved plan and only under the owner's explicit bootstrap authorization.
- Application plans/applies run only through protected GitHub Environments.
- Development verification precedes production eligibility.
- Billable application provisioning still needs explicit cost approval.
- DSQL runtime identity and credential refresh require live development verification before production.
- An unrelated account-level personal workload is out of scope and must not appear in plan changes or evidence.
