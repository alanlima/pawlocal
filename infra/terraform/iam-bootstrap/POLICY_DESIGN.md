# Terraform role policy design

This root owns the shared GitHub OIDC provider, GitHub role identity/trust, baseline permissions, permissions boundaries, runtime identities, and the private saved-plan transfer bucket. Development and production roots own application resources and only their matching managed policies and attachments. Configuration is not evidence of an apply.

## Environment plan roles

Each plan role trusts only its exact `<environment>-plan` GitHub Environment subject; those Environments are restricted to `main`. It can read the matching state, manage only that state's lock object, perform provider refresh reads, and upload only to `plans/<environment>/`. It has no application-service mutation actions and no IAM write actions.

## Environment apply roles

Each apply role trusts its protected `<environment>-apply` GitHub Environment. The production apply role also trusts exactly `production-destroy-prepare` and `production-destroy`, preserving the two separately protected approvals used by the standard destroy workflow; no development destroy subject is trusted. Bootstrap grants state/plan access and narrowly scoped IAM policy administration so the environment root can create/update its fixed-name application, frontend-publish, and runtime policies. The boundary limits policy and role administration to the matching environment's stable name prefixes. The role's inline identity policy is narrower: it names the exact matching policy ARNs, role ARNs, and `iam:PolicyARN` attachment combinations.

Shared IAM policy, boundary, trust, and attachment construction must be driven from the environment metadata and must not branch on literal environment names to include or omit a required deployment capability. Every environment receives the same required policy families and boundary capabilities, while its ARNs, state key, role names, and OIDC subjects remain exact and isolated. Environment-specific workflow subjects belong in the environment metadata; they do not authorize the other environment or imply that both environments expose the same workflows.

The bootstrap-owned boundary is the effective maximum. It does not allow role creation/deletion, trust changes, permissions-boundary changes, `PassRole`, OIDC changes, another environment's state, policies, attachments, DNS names, or named resources.

## Delegated Cognito provider roles

DEC-009 keeps Lambda and log-group lifecycle outside the already size-constrained environment apply boundary. For each environment, bootstrap owns the following separate roles:

| Role | Exact trust | Maximum authority |
|---|---|---|
| `pawlocal-<environment>-cognito-terraform-plan` | Only the matching `pawlocal-<environment>-terraform-plan` role through `sts:AssumeRole`; no direct GitHub OIDC trust. | Provider reads required to refresh the exact deterministic Lambda function and log group, plus the approved account-region `logs:DescribeLogGroups` metadata exception. No write, permissions-management, state, plan-transfer, Cognito, log-content read, or cross-environment mutation access. |
| `pawlocal-<environment>-cognito-terraform-apply` | Only the matching `pawlocal-<environment>-terraform-apply` role through `sts:AssumeRole`; no direct GitHub OIDC trust. | Exact matching Lambda and log-group lifecycle plus exact-role `iam:PassRole` conditioned on `iam:PassedToService = lambda.amazonaws.com`, together with the approved account-region `logs:DescribeLogGroups` metadata exception. It has its own bootstrap-owned permissions boundary and no state, plan-transfer, Cognito, log-content read, or cross-environment mutation access. |
| `pawlocal-<environment>-cognito-pre-signup` | Only the `lambda.amazonaws.com` service principal. | `logs:CreateLogStream` and `logs:PutLogEvents` only for streams beneath `/aws/lambda/pawlocal-<environment>-cognito-pre-signup`; no Cognito or other application API authority. |

The delegated plan identity policy, delegated apply identity policy, and delegated apply permissions boundary each contain a dedicated Logs metadata statement. Its action list is exactly `logs:DescribeLogGroups`, its resource list is exactly `*`, and its `StringEquals` condition requires `aws:RequestedRegion` to equal the configured AWS region. Do not combine it with another action or broaden it to `logs:Describe*` or `logs:*`. AWS exposes no resource, tag, or request-prefix condition for this action. The provider still supplies the deterministic matching `LogGroupNamePrefix`, but that request parameter cannot be enforced by IAM. The owner accepts the resulting account-region log-group metadata visibility.

That exception grants no log-content or stream read: it excludes `logs:DescribeLogStreams`, `logs:GetLogEvents`, `logs:FilterLogEvents`, `logs:GetLogRecord`, `logs:GetLogGroupFields`, `logs:StartQuery`, `logs:GetQueryResults`, `logs:StartLiveTail`, and `logs:Unmask`. `logs:ListTagsForResource` and every create, tag, update, retention, and delete operation remain in separate exact-resource statements limited to the matching log-group ARN. Cross-environment mutation remains denied. Lambda reads and mutations remain exact-resource; no Lambda statement uses `Resource = "*"`.

The existing environment plan and apply identity policies add only `sts:AssumeRole` for their exact matching delegated role. Their effective permission remains the intersection with their existing controls. They receive no direct Lambda or Logs mutation and no direct `iam:PassRole`; the existing environment apply boundary is neither enlarged for those actions nor weakened to make room for them.

The delegated apply role's identity policy and dedicated boundary must both authorize an operation. Lambda permissions use the deterministic matching function ARN. Apart from the dedicated regional `logs:DescribeLogGroups` statement, CloudWatch Logs permissions use the deterministic matching log-group ARN and required stream suffix. Creation requests require the approved project/environment tags, and follow-on operations remain exact-resource and environment-isolated. The only passable role is the matching pre-sign-up execution role, and only when passed to Lambda. The dedicated boundary is tested independently against the AWS 6,144-byte managed-policy maximum and does not consume space in the existing environment boundary.

### Provider 6.69.1 action evidence

The bootstrap lock file selects AWS provider `6.69.1`. Its implementation gives the following configured-resource call set:

| Terraform resource | Refresh calls | Configured create/update/delete calls |
|---|---|---|
| `aws_lambda_function` | `GetFunction`, `GetFunctionCodeSigningConfig`, and `ListTags` | `CreateFunction`, `UpdateFunctionCode`, `UpdateFunctionConfiguration`, `DeleteFunction`, `TagResource`, and `UntagResource` |
| `aws_lambda_permission` | `GetPolicy` | `AddPermission` and `RemovePermission` |
| `aws_cloudwatch_log_group` with finite retention and no KMS key or deletion protection | `DescribeLogGroups` with the exact `LogGroupNamePrefix`, plus `ListTagsForResource` | `CreateLogGroup`, `PutRetentionPolicy`, `DeleteLogGroup`, `TagResource`, and `UntagResource` |

The evidence is the provider's version-pinned [Lambda function](https://github.com/hashicorp/terraform-provider-aws/blob/v6.69.1/internal/service/lambda/function.go), [Lambda permission](https://github.com/hashicorp/terraform-provider-aws/blob/v6.69.1/internal/service/lambda/permission.go), [Lambda tag helper](https://github.com/hashicorp/terraform-provider-aws/blob/v6.69.1/internal/service/lambda/tags_gen.go), [log-group resource](https://github.com/hashicorp/terraform-provider-aws/blob/v6.69.1/internal/service/logs/group.go), and [Logs tag helper](https://github.com/hashicorp/terraform-provider-aws/blob/v6.69.1/internal/service/logs/tags_gen.go). Optional branches for concurrency, code signing mutation, KMS association, log-group deletion protection, durable execution, and Lambda publishing are excluded because Issue #187 does not configure those features.

`DescribeLogGroups` is account/region list authorization and has no resource type in the AWS authorization table, which is why the owner-approved statement requires `Resource = "*"` with the configured-region condition. The provider still supplies the exact prefix. AWS also documents two ARN forms for a log group: most actions use the form ending in `:*`, while `TagResource`, `UntagResource`, and `ListTagsForResource` require the same exact log-group ARN without that suffix. The policies keep both forms deterministic and matching-environment-only. See the [CloudWatch Logs authorization reference](https://docs.aws.amazon.com/service-authorization/latest/reference/list_logs.html) and [LogGroup API ARN guidance](https://docs.aws.amazon.com/AmazonCloudWatchLogs/latest/APIReference/API_LogGroup.html).

Bootstrap exposes `cognito_terraform_role_arns`, keyed by environment and then `plan`/`apply`, and `cognito_pre_sign_up_role_arns`, keyed by environment. These outputs are reviewed post-apply evidence that the created roles match the deterministic contract; environment workflows do not consume them as runtime configuration. Development and production application states own the Lambda package/function, finite-retention log group, Cognito invoke permission, user pool, clients/domains, environment policies, and matching attachments. The delegated roles own no application resource and receive no state access.

The environment root configures `aws.cognito_deployment` with the stable shared-config profile `pawlocal-cognito-deployment`. Workflows create that profile outside the repository with `credential_source = Environment`, the constructed matching role ARN, a purpose-specific session name, and `duration_seconds = 3600`. Plan and destroy-plan jobs normalize their purpose to `plan`; apply, teardown-preparation apply, and destroy-apply jobs normalize it to `apply`. The default provider continues to use the existing environment role, and workflows do not set a global `AWS_PROFILE`.

The repository currently targets the commercial AWS partition: existing workflow identity validation requires `arn:aws:iam::...`. Each job therefore sets the workflow-local constant `AWS_PARTITION=aws`, validates the existing protected `PAWLOCAL_AWS_ACCOUNT_ID` as exactly 12 digits and the selected environment as exactly `development` or `production`, and constructs `pawlocal-<environment>-cognito-terraform-<plan|apply>` plus `arn:${AWS_PARTITION}:iam::<PAWLOCAL_AWS_ACCOUNT_ID>:role/pawlocal-<environment>-cognito-terraform-<plan|apply>`. No new GitHub repository or Environment variable supplies a delegated or execution-role ARN.

Before writing the temporary config, the job validates the normalized purpose and constructed delegated role name and ARN. It masks that ARN before later steps and verifies the delegated caller identity after creating the profile. Diagnostic steps blank the delegated role ARN, `AWS_CONFIG_FILE`, and profile name. A final `if: always()` step deletes the temporary config. Bootstrap outputs are verification evidence only and are never copied into GitHub variables or read by these jobs.

The environment Terraform input `cognito_pre_sign_up_role_arn` is nullable with default `null`. In the default path, Terraform derives the effective ARN from `data.aws_partition.current.partition`, `data.aws_caller_identity.current.account_id`, and the selected environment, with the exact role name `pawlocal-<environment>-cognito-pre-signup`. Workflows do not set `TF_VAR_cognito_pre_sign_up_role_arn` by default. A non-null override is allowed only for a separately approved need and must validate against that exact current-partition, current-account, matching-environment role identity. The effective default or validated override is used consistently as the Lambda execution role and as the sole `iam:PassRole` resource in the delegated apply identity policy and boundary; an override cannot broaden pass-role authority.

The delegated assume-role hop is role chaining and can last no more than one hour. Each Terraform operation starts with fresh credentials and must complete within that window. Expired or interrupted operations fail closed and require a newly generated and reviewed saved plan. See the AWS [role chaining guidance](https://docs.aws.amazon.com/IAM/latest/UserGuide/id_roles.html) and [assume-role credential-provider reference](https://docs.aws.amazon.com/sdkref/latest/guide/feature-assume-role-credentials.html).

Bootstrap boundaries must not depend on generated full resource ARNs. Write ceilings use stable scoped ARNs for the intended resource family or a deterministic environment/name prefix. `Resource = "*"` is reserved for AWS create actions that do not support resource-level authorization and are request-tag constrained wherever supported, plus the dedicated configured-region `logs:DescribeLogGroups` metadata statement above. Exact generated ARNs belong in the narrower environment-owned policies after creation; the intersection keeps effective access exact without rewriting the bootstrap boundary.

AWS limits a managed-policy document to 6,144 non-whitespace bytes. The repository enforces a stricter 6,100-byte budget against each rendered, minified environment apply boundary and verifies the environment-owned application policy against the AWS limit. A synthetic length-equivalent fixture prevents shorter placeholder inputs from hiding the reviewed shape. Both environment boundaries include the matching frontend-object deletion ceiling so bootstrap can support the same Terraform-owned lifecycle without being reapplied in a particular environment order. The exact environment identity policy remains limited to its own named policy and bucket family, and teardown remains default-off in the environment root and protected workflow. The exact environment identity policies still narrow effective administrative connection and role-assumption access to the matching cluster and runtime role. Boundary statements omit non-authorizing SIDs and use read-only service patterns; compact Cognito and Lightsail action families fit the policy-size limit while the matching identity policy retains the exact mutation actions. Post-create mutations use only compatible DSQL cluster, Cognito user-pool, Lightsail certificate, and Lightsail container-service resource families. DSQL and Lightsail retain matching authorization-tag conditions; Cognito's listed user-pool client/domain mutation actions support the user-pool resource type but do not list action-level condition keys. The boundary requires matching project/environment authorization tags where the AWS service supports them, while the environment-owned identity policy requires the approved tag-key set and exact generated resources after handoff. S3 creation additionally requires every metadata tag value in both the create and dependent tag authorization. Effective permissions are always the intersection of the stable boundary and the narrower identity policy.

| Service | Maximum environment authority |
|---|---|
| S3 | `CreateBucket` and its provider-required `TagResource` authorization are both restricted to the matching `pawlocal-<environment>-` prefix, exact tag keys, and the complete expected tag values. An untagged provider fallback therefore remains denied. `PutBucketTagging`, configuration mutation, cleanup, and the provider's exact name-scoped pre-tag reads stay inside that stable environment bucket-name family. The environment-owned publisher policy narrows effective object access to the exact generated bucket. No broad `s3:Get*` is granted. |
| Aurora DSQL | Tagged `CreateCluster` and its dependent `TagResource` authorization require the exact eight-key cluster payload: the six common application tags plus the environment-specific `Name` and fixed database `purpose`. A missing, extra, or incorrect tag fails closed. Update/delete/policy actions require matching resource tags. The bootstrap runtime boundary uses the account/region cluster family with matching project/environment tags; the environment-owned runtime policy narrows effective connection access to the exact generated cluster. |
| Lightsail | Tagged container-service and certificate creation includes the dependent `TagResource` authorization. Those dependent checks use AWS's pre-creation `ContainerService/*` and `Certificate/*` resource forms, constrained by matching request and authorization tags plus the approved tag-key set. Update/deployment/delete requires matching resource tags, and `UntagResource` is never granted. Provider create/delete waiters can read the exact operation with `GetOperation`; the plural `GetOperations` remains discovery-only. |
| CloudFront | The stable boundary admits tagged distribution creation, exact-name function management, and separate post-create ceilings for distributions and OACs. Distribution update/delete uses the account distribution family plus matching project/environment resource tags. OAC update/delete uses the account OAC family because OAC IDs are generated, their ARNs have no deterministic name segment, and CloudFront exposes no supported OAC tag condition. The environment-owned application policy remains exact-resource, so the effective permission after handoff is limited to the matching distribution and OAC. Distribution actions and OAC actions never share a statement, and `UntagResource` is never granted. |
| Cognito | Tagged user-pool creation includes the dependent `TagResource` authorization against AWS's required `userpool/*` pre-creation resource form, with matching request tags and absent authorization tags. Follow-on management requires matching resource tags. |
| Route 53 | Changes are limited to the configured zone, the environment frontend/API/validation names, and A/AAAA/CNAME types. |

The normal workflow plan guard rejects deletes and replacements except the provider's expected immutable Lightsail deployment-version replacement. A future destructive infrastructure change requires separate scope and authorization; the boundary alone is not authorization to apply it.

## Publisher and runtime identities

Bootstrap declaratively imports only the read-only-inventory-verified development publisher role when `import_existing_development_deploy_role=true`. The production publisher is created normally. Both trust only their matching release GitHub Environment and use their matching bootstrap-owned environment boundary. Environment roots create the exact frontend publication policy and attachment after their frontend resources exist.

The three app-specific managed policies present in the populated bootstrap state (development frontend, production frontend, and development runtime) have explicit `removed` blocks with `destroy = true`; the reviewed bootstrap plan must delete exactly those three policies rather than preserve duplicate ownership. The additional `identity_production_runtime` removed address is defensive because that resource existed only on an unapplied change and must be a no-op against the populated state. Bootstrap retains only identity, trust, baseline, boundary, and shared plan-transfer ownership. Environment roots are the sole owners of application, frontend-publish, and runtime policies and matching attachments.

The reviewed bootstrap plan must also delete exactly the two legacy `environment_service_apply` inline role policies. Those deletions intentionally remove the former inline application authority now replaced by bootstrap boundaries and environment-owned policies. The existing development app-role boundary keeps its state-compatible description so the policy updates in place; no other delete or replacement is allowed.

The first bootstrap apply partially completed before the environment apply boundaries were created, and the remote state serial advanced. Its saved plan is stale and must never be retried. The two environment apply-boundary creates and eight dependent environment Terraform role/inline-policy updates described by the earlier recovery were the expected shape at that historical checkpoint; they are not automatically accepted in an Issue #186 plan. Before this change can merge, a fresh normal-refresh plan must reconcile the current state and show only the approved delegated Cognito roles, boundaries, policies, outputs, and exact assume-role additions. Any still-pending earlier action, import, delete, replacement, application resource, unrelated resource, or additional drift is a hard stop for separate investigation and review.

The publisher and runtime boundaries use stable resource families from the first bootstrap plan: the matching environment S3 name prefix, the account CloudFront distribution family with matching resource tags, and the regional account DSQL cluster family with matching resource tags. Environment roots create and attach the exact bucket/distribution and cluster policies after those resources exist. Their intersection with the boundary retains exact effective access without requiring a second bootstrap boundary rewrite.

Development and production runtime roles are still created only after bootstrap receives the exact Lightsail `principal_arn` from the matching foundation output. This is a trust-principal handoff, not a permissions-boundary resource handoff or an exception to the stable-boundary rule. The environment root creates the exact DSQL connection policy and attachment. No generated application resource ARN is an input to a bootstrap-owned boundary.

## Saved plan handling

Plan roles upload opaque plans and metadata only beneath their environment prefix. Apply roles can only read that prefix. Metadata binds the plan SHA-256 to repository ID, commit, run, attempt, environment, state key, and a one-way account/backend/region fingerprint. GitHub summaries contain only resource type/action/count. Raw provider logs, raw plan JSON, plan binaries, Terraform state, credentials, secret values, account identifiers, and resource identifiers are not public evidence.
